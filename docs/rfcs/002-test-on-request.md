# RFC 002 — Тестирование по запросу

Статус: Draft v0.3. Дата: 2026-11-03. Реализация skill v0.1: [test-on-request](../../skills/test-on-request/SKILL.md).

## Решение

Добавить явно включаемый skill с тремя видами проверок: public и private создаются до целевого решения, adversarial — после фиксации решения. Общие правила описаны в skill, форматы и жизненный цикл — в [протоколе](../../skills/test-on-request/references/protocol.md), требования к protected evaluator — в [границах изоляции](../../skills/test-on-request/references/private-evaluation.md).

Skill не активируется от любого изменения кода. Пользователь может запросить отдельную операцию или полный цикл. В v0.1 реализованы инструкции, CLI init/freeze/verify/brief, шаблоны передачи результатов и проектные native entrypoints. Защищённый runner, registry и enforcement — отдельные будущие компоненты harness.

Обязательное уточнение пользователя в v0.2: **все тесты генерирует другой агент**. Разработчик передаёт минимальный task brief и получает готовые публичные тесты, результаты и разрешённые контрпримеры. Черновики, перебор гипотез и отладка тестов остаются в worker-контексте. Полная история разработчика не наследуется; public/private/adversarial используют отдельные контексты генерации. См. [контракт делегирования](../../skills/test-on-request/references/delegation.md).

Если подходящего отдельного агента нет, генерация отмечается `generation_unavailable`; она не переносится молча в контекст разработчика. Это правило не заменяет техническую изоляцию private-материалов. Готовые проверки может исполнять детерминированный runner без дополнительного LLM.

## Почему не стоит намеренно ослаблять public tests

Предположение пользователя указывает на реальный риск: решение может подстроиться под известные примеры и не выполнять общий контракт. Но слабые public tests уменьшают полезную обратную связь и позволяют пропустить очевидные регрессии. Это не устраняет адаптацию к тестам.

Предлагаемая политика: **все требования открыты; конкретные случаи и комбинации могут быть скрыты**. Публично показываются семантика, важные границы, representative examples и свойства. Private расширяет пространство случаев в рамках тех же требований. Adversarial исследует слабости конкретной реализации. Фиксированный процент «публичного покрытия» не нужен; полный публичный перебор малого домена допустим и полезен.

Для обычного coding agent здесь чаще речь о подстройке решения по обратной связи в текущем процессе, а не об обучении весов модели. Скрытый набор тоже может перестать быть независимой оценкой при многократных запросах и исправлениях. Исследование adaptive holdout относится к статистическим данным; перенос идеи на оценку кода — архитектурная аналогия, не формальная гарантия этого skill. [Google Research, The reusable holdout](https://research.google/blog/the-reusable-holdout-preserving-validity-in-adaptive-data-analysis/).

## Сквозной пример: TTL-кэш

Открытый контракт: `get` возвращает свежую запись без loader; при `now >= expires_at` вызывает loader; чтение не продлевает TTL; `invalidate` удаляет запись; ошибки loader выходят наружу и не кэшируются.

- Public до решения: повторное чтение свежей записи, ровно граница TTL, invalidate и ошибка loader. Важные края не скрываются ради затруднения задачи.
- Private до решения: иные ключи/времена, комбинации invalidate/reload, заранее зафиксированные генераторы последовательностей и expected behavior. Это иллюстрация классов, не реальный секретный пакет.
- Adversarial после решения: видит, что ветка fresh-hit перезаписывает expires_at, и строит последовательность повторных чтений. Если срок сдвигается, показывает нарушение известного требования, а не придумывает новое.

Property-based testing задаёт свойства для входного домена, stateful testing ищет ошибки в последовательностях операций; инструменты могут применяться в любом из трёх видов тестов. Видимость и время создания не определяют технику тестирования. [Hypothesis](https://hypothesis.readthedocs.io/en/latest/), [stateful tests](https://hypothesis.readthedocs.io/en/latest/stateful.html).

## Архитектура и trust boundary

Native agent работает с public contract и public tests. Доверенный evaluator владеет private package и oracle, принимает immutable candidate, запускает его с ограниченными правами и выпускает разрешённый результат. Adversarial tester получает frozen candidate и public contract; доступ к private suite ему не нужен.

Отдельная папка, worktree и subagent с теми же правами не обеспечивают приватность. Код решения также может читать доступные runtime-данные: для усиленной гарантии oracle и весь suite должны оставаться в другом процессе/сервисе. Переданный текущий input сам по себе не скрывается от исполняемого решения. Полная модель угроз и журнал disclosure важнее названия каталога `private`.

## Раскрытие и следующий цикл

По явному выбору пользователя private failure немедленно раскрывается как минимальный воспроизводимый пример и превращается в public regression. Это предпочтение улучшает исправление ошибок, но снижает независимость повторной оценки на том же наборе.

Сохраняются исходный run, candidate ID, версия suite и disclosure event. После исправления создаётся новый candidate. Если нужен свежий итоговый verdict, используется ещё не запрашивавшийся reserve, подготовленный заранее. Если reserve отсутствует, повторные результаты публикуются как адаптивная оценка без заявления о свежем holdout.

## Поэтапная реализация

1. Реализовано v0.1: skill с явной активацией, public/adversarial через отдельных native workers, CLI подготовки и content-addressed snapshot, шаблоны результатов и проектные entrypoints Codex/Claude. Private brief возвращает unavailable; snapshot проверяет drift, но не даёт изоляции. См. [исполнение](../../skills/test-on-request/references/execution.md).
2. Следующий технический шаг: доказать границу evaluator на одной задаче с небольшим public input/output контрактом, затем добавить CLI над существующим test runner и evidence format. Не строить универсальную песочницу в тексте skill.
3. После подтверждения: подключить runners и adapters, enforceable budgets, trusted package registry и controlled declassification. Нативные agent loops сохраняются.

## Приёмочные сценарии для самого skill

- Обычный запрос изменить код не активирует workflow; явный public/attack/full выбирает нужный scope.
- Генератор работает в отдельном контексте без полного transcript разработчика; обратная передача не содержит рабочих черновиков и логов генерации, но сохраняет готовые тесты, существенные ограничения и вопросы.
- При отсутствии делегирования генерация не выполняется самим разработчиком как незаявленный fallback.
- Existing solution не получает ложную метку pre-implementation tests.
- Все скрытые assertions соответствуют открытому контракту; неоднозначность возвращается как needs_spec_decision.
- При общих правах на «private» каталог private verdict недоступен, а не pass.
- Раскрытый пример появляется публично, происхождение и прежний провал сохраняются; повторный запрос не обнуляет query budget.
- Старый verdict не переносится на изменённый candidate; flaky/infra failure не маскируются под продуктовый баг.
- Adversarial no findings сопровождается бюджетом и не становится доказательством отсутствия ошибок.

Это расширенный план оценки: прохождение технических проверок v0.1 не означает, что каждый сценарий уже испытан или что private backend реализован. Фактические результаты сохраняются отдельно в evals/test-on-request/.
