Как я понял задачу

Результат исследования: первым пилотом предлагается semantic top-20 → LLM reranking/фильтрация → top-5, затем условный query rewriting. На 100 synthetic документах и 28 answerable запросах reranking поднял Recall@5 с 96.43% до 100%, nDCG@5 с 93.38% до 100%; 4/4 no-answer случая отклонены. Rewriting и HyDE дали одинаковый Recall@5=100%, decomposition при общем включении снизила его до 92.86%. Это небольшой development эксперимент, не доказательство production выигрыша. Оптимизацию начать с представления векторов и повторных вычислений; полный Rust rewrite пока не обоснован. Рабочее ядро не изменялось.

По источнику

Существующий development corpus проверяется повторно. Новый публичный synthetic engineering corpus: 100 документов, 32 запроса, relevance labels зафиксированы отдельным автором до измерений. 28 answerable и 4 no-answer; есть exact, paraphrase, multilingual и multi-fact slices. 06 · Подход и альтернативы

Предложение

Приоритет по результатам: (1) пилот второй стадии с контролем no-answer; (2) один rewrite условно, с original branch; (3) decomposition только как проверяемая гипотеза для сложных multi-fact задач; (4) HyDE opt-in, потому что на этом наборе не превзошёл более короткий rewrite. Дешёвый локальный cross-encoder — отдельный будущий эксперимент, native LLM пока служит проверкой качества подхода.

E1
По источнику

Kernel microbenchmark 1000×384: JSON parse+validation+normalization+Python dot median 128.96 мс; повторно используемая нормализованная NumPy float64 матрица — 0.069 мс. Однократная подготовка матрицы 123.81 мс, размер 3.07 МБ; top-20 совпал, max score delta=4.2e-17. Это показывает потенциал устранения повторов и векторизации, но не ускорение всей системы: SQL, freshness, invalidation, sorting и restart сюда не входят.

E1
Предложение

Сначала оптимизировать измеренные повторные вычисления: повторный lexical retrieval в hybrid, чтение/декодирование всех current records, JSON vectors, повторную нормализацию и Python dot-products. Сравнить векторизованный exact search, бинарное представление производного индекса и ограниченную SQL-выборку; формат источника истины SQLite сохранять до доказанной необходимости.

C1 C2
Предложение

Query planner — отдельный native шаг перед retrieval. Предлагаемый QueryPlan v1: original, literal identifiers, optional rewrite, bounded subqueries, optional hypothetical_document, reason и бюджет. LLM создаёт данные; Core проверяет размер/форму, фиксирует task/snapshot, запускает разрешённые ветви и сохраняет trace. При недоступности planner выполняется исходный поиск.

Предложение

Rewriting: один вариант для неясных/разговорных/межъязыковых запросов с сохранением исходного поиска. Decomposition: 2–4 самостоятельных подзапроса только для задач с несколькими фактами. Exact ID/path/symbol branch защищается от вытеснения. Количество вариантов не должно автоматически увеличивать вес одного источника при fusion.

W1 W2
Предложение

Двухстадийный поиск: retrieve top-N → union/dedup → rerank → final top-k → повторная проверка eligibility → Scout/packet. Оценивать baseline и reranked на одном candidate pool. Reranker не способен восстановить документ, который не попал в кандидаты; поэтому отдельно измерять candidate recall и качество порядка.

U3 W2
Предложение

HyDE оставить экспериментальной опцией для абстрактных описаний и низкого recall. Гипотетический документ кодируется document encoder и служит только поисковым сигналом, не попадает в БД как знание и не подменяет evidence. Для точных API/версий/состояния сначала обычный поиск.

W3
Предложение

Полный Rust rewrite пока не выбирать. SQLite и ONNX уже выполняют тяжёлую работу вне Python; сначала нужен профиль остаточной стоимости после алгоритмических улучшений. Если CPU всё ещё доминирует, сравнить узкий Rust-компонент со векторизованным Python на том же контракте и workload.

C2 C4 E2

07 · Эксперименты и оценка

По источнику

Основное сравнение (28 answerable, 4 no-answer отдельно): semantic Recall@5/nDCG@5=96.43/93.38%; original+rewrite=100/96.32%; original+decomposition=92.86/90.31%; original+HyDE=100/96.32%; semantic+rerank=100/100%; original+rewrite+decomposition+rerank=100/100%. Варианты сохраняют original, используют RRF и exact-identifier protection.

E1
По источнику

Rerank улучшил порядок по nDCG у 5 из 28 запросов, не ухудшил ни одного; Recall улучшился только у одного. Exploratory 95% paired-bootstrap интервал прироста Recall: [0;10.71] п.п.; nDCG: [0.57;15.72] п.п. Все три candidate pools имеют Recall@20=100%. Комбинация всех техник не дала дополнительного выигрыша относительно rerank без transforms; эффект ограничен потолком набора.

E1
По источнику

Это native LLM reranking + relevance filtering + abstention, один blind проход, 73 уникальных pool/query пакета, 96 сравнений. Корпус/qrels и исходные scores не передавались reranker. Production latency, токены и стоимость reranker не измерены; отдельный cross-encoder не тестировался.

E1
По источнику

HyDE run использовал hypothetical-text query path; на всех 32 зафиксированных текстах проверена побитовая эквивалентность query/document embeddings текущего bundle (max abs delta=0). Вывод относится только к этой модели и этим текстам; Hypothetical documents не сохранялись как факты.

E1
По источнику

В harness эксперимента сначала использовалась метка exact_symbol для закрепления первого результата. После аудита правило заменено проверкой реального совпадения query с ID/ref/symbol. Сохранён исходный v1, пересчитаны результаты: все rankings/metrics и rerank input/mapping совпали. Метки больше не используются для маршрутизации.

E1
По источнику

Исходный correctness suite: 124 теста прошли совокупно; три preview tests повторно запущены с разрешением loopback после sandbox PermissionError. Дополнительно прошли 5 новых post_hoc freshness tests. Изменений продукта не было.

E1
Предложение

Качество: Recall@5 — доля релевантных документов в первых пяти; nDCG@5 — качество их порядка; MRR@5 — позиция первого релевантного; complete evidence coverage — все факты multi-fact запроса. Для no-answer считать abstention отдельно: top-k выдача сама по себе не доказывает наличие ответа.

Предложение

Ablation: raw lexical/semantic/hybrid, original+rewrite, original+decomposition, комбинация, original+HyDE; затем одинаковые pools до/после rerank и комбинация с transformations. Показать per-query wins/ties/losses, интервалы paired bootstrap при доступности; выбор лучшего на этом наборе является adaptive development, не независимым подтверждением.

Предложение

Скорость: warm query-cache hit, warm model/cache miss, fresh-process CLI отдельно; последовательный interleaved порядок, median/p95 и число повторов. Масштаб: 100/1000, при бюджете 5000 synthetic записей. Профиль Python, SQL count и RSS связываются с dataset/code/model hash.

По источнику

Correctness: существующие suites плюс отдельные post_hoc проверки TTL/dependencies/revocation. Для будущих оптимизаций нужны differential parity и failure-injection: model failure, stale index, concurrent revoke/source drift, ordering, transaction rollback, restart/idempotency. Protected private evaluator отсутствует; это не означает, что private suite пройден.

09 · Ресурсы и ограничения

По источнику

Matched warm workload (8 фиксированных запросов × 3, n=24 на режим): semantic median/p95 16.07/16.61 мс при 100 документах, 161.13/177.68 мс при 1000. Fresh-process semantic без query-cache: median 1223 мс (n=3); с cached query около 200 мс. Это разные условия, их нельзя объединять в один latency показатель.

E1
По источнику

Локальный CPU, существующая MiniLM; новые веса не загружаются. Замеры выполняются последовательно, дополнительная память ограничена примерно 2GiB, один benchmark — 300 секунд. Для увеличения размера нужно отдельное основание, а не автоматический перебор.

E1
Неизвестно

Целевая допустимая задержка и размер будущей базы не заданы. Пороги выигрыша для Rust и reranker предстоит согласовать на реальном workload; исследовательские цифры не превращаются в SLA.

12 · Риски и открытые решения

Предложение

Маленький synthetic корпус может давать потолок recall и завышать эффект rerank. Query rewriting способен стереть отрицания/версии; decomposition — потерять связь между фактами; HyDE — направить поиск к вымышленному устройству системы. Обязательны исходная ветвь и отдельные регрессионные slices.

Предложение

Оптимизации prefilter/caching могут ускорить поиск ценой утечки foreign/stale данных. Rust добавляет стоимость FFI, сборки/доставки и риск расхождения семантики. Эти риски проверяются до использования живой БД.

Неизвестно

Offline native-agent rerank не равен внедрённому cross-encoder. Выбор production reranker и его latency/cost ещё не измерены.

G3
Предложение

Корпус scaling не моделирует большие графы file/knowledge dependencies, высокую конкуренцию и поток записей. Production стоимость source hashing и cache invalidation требует отдельной нагрузки.
