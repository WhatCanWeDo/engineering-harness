# Приватность тестов и доверенный evaluator

Требование «агент не видит приватные тесты во время разработки» должно поддерживаться правами и потоком данных. Текст skill помогает пользоваться границей, но не создаёт её.

## Участники

| Роль | Доступ |
|---|---|
| Пользователь | Задача, разрешения, результаты и политика раскрытия |
| Разработчик | Публичный контракт, public tests, рабочая копия и разрешённые раскрытые примеры |
| Генератор public | Отдельный агент: контракт, интерфейсы и разрешённый baseline; возвращает готовые публичные тесты |
| Автор private | Контракт и необходимые интерфейсы/baseline; подготовка до целевого решения; защищённое хранилище |
| Evaluator | Зафиксированный private package, oracle, изолированный запуск candidate, журнал evidence |
| Adversarial tester | Зафиксированное решение и публичный контракт; private package ему не нужен |

Генерация каждого типа тестов обязательно выполняется отдельным от разработчика агентом с минимальным входным контекстом. Генераторы public/private/adversarial используют разные worker-контексты по [контракту делегирования](delegation.md). Сам evaluator и исполнение готовых тестов могут быть обычным процессом или CI: отдельный LLM для запуска не требуется. Одинаковые filesystem/tool permissions не дают приватности, даже когда контексты генерации разделены.

## Минимальная и усиленная границы

**Development isolation:** разработчик не может прочитать private package через filesystem, git history, terminal, retrieval, tool outputs, CI artifacts или историю разговоров. Автор private не должен быть тем же продолжающим разработку контекстом: уже прочитанное нельзя «забыть» инструкцией.

**Runtime isolation:** если требуются гарантии и против сгенерированного кода, oracle и весь private suite не загружаются в тот же интерпретатор, где исполняется candidate. Иначе код может читать стек, переменные или файлы тестового процесса даже при read-only mount. Grader держит oracle отдельно, передаёт candidate ограниченный запрос через процессную/RPC-границу и сравнивает выход с ожидаемым вне candidate.

Candidate неизбежно видит переданный ему текущий вход. Цель — скрыть весь пакет, labels/oracle и будущие случаи, а также не вернуть текущие входы разработчику вне политики раскрытия. Состояние запуска эфемерно, сеть/выходы ограничены, сырые stdout/stderr не пересылаются автоматически. Одно лишь нахождение тестов вне agent workspace не обеспечивает эти свойства.

Для задач с произвольными in-process unit tests усиленная граница может быть несовместима с текущим harness. Тогда заявить более слабую гарантию явно или отметить защищённый private backend недоступным. Не выдавать контейнер с общими mounts, credentials или Docker socket за достаточную изоляцию.

## Проверка capabilities до private

Доверенный backend должен сообщать и подтверждать:

- Кто может читать/изменять private package и oracle, и как разработчик лишён этих прав.
- Как подтверждаются версия пакета до разработки и неизменность критериев.
- Как воспроизводится candidate и что исключает незаметное изменение snapshot.
- Какие права у исполняемого кода; как отделены oracle и защита private данных от runtime.
- Какие поля результатов доступны разработчику, где хранятся raw logs, как выпускается reproducer.
- Как ведутся query budget, disclosure ledger, versions и ограничения ресурсов.

В первой версии skill такой backend не создаётся автоматически. Отсутствие возможности — `unavailable`, а не имитация «закрытых тестов» в соседнем каталоге. План и public/adversarial могут быть полезны независимо от private ветки.

## Разрешённое раскрытие

Пользователь заранее выбрал немедленное раскрытие минимального воспроизводимого примера при провале. Evaluator выпускает именно этот разрешённый reproducer с ожидаемым поведением и requirement ID, а не полный private stack trace, весь dataset или сырые логи. Если private data требуют дополнительных ограничений, они должны быть определены в контракте до запуска; skill не расширяет существующие права доступа.

Раскрытый случай становится public regression с сохранением private-origin. Изменение статуса видимости записывается отдельно от исходного sealed package. У оставшихся закрытых случаев нет автоматической гарантии свежести: журнал показывает, какая обратная связь уже была использована.

## Что хранить в обычном репозитории

Допустимы публичный контракт и план, public/regression tests, adversarial reproducers, публичные summary и opaque references на защищённые evidence. Приватные tests, seeds, oracle, полный набор expected outputs и сырые логи туда не попадают. Нельзя помещать их в HTML-объяснение дизайна, доступное разработчику, или в общую память.
