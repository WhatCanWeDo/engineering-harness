# План проектирования Engineering Harness

Дата: 2026-11-03. Статус: предложенная повестка для обсуждения.

Основание — [RFC 001, Draft v0.1](rfcs/001-native-first-agent-agnostic-engineering-harness.md). Этот план не меняет статус RFC и не фиксирует стек реализации.

Текущий первый эксперимент — [understand-changes](../skills/understand-changes/SKILL.md): объяснение изменений с настраиваемыми предпочтениями и HTML quiz. Для его проверки подготовлена [рубрика оценки skills](skill-evaluation.md). Наличие рабочего skill ещё не означает готовность всей Portable Foundation или проверенную интеграцию с двумя агентами.

## Текущее решение: тестирование по запросу

[RFC 002](rfcs/002-test-on-request.md) описывает второй skill: public/private/adversarial тесты по явному запросу, раскрытие найденного private-контрпримера в публичный regression и требования к независимому evaluator. Реализована v0.1 с отдельными генераторами, CLI подготовки/фиксации candidate и проектными entrypoints. Protected runner пока является проектируемой capability.

## Следующее обсуждение: Portable Foundation

Новая тема по запросу пользователя — [RFC 003, Knowledge & Context Layer](rfcs/003-knowledge-context.md). Подтверждены автоматическое сохранение evidence/candidates, review спорных обобщений и перенос между проектами только общих знаний. Предложен локальный MVP с Scout/Curator и role packets; база и автоматизация пока не реализованы.

Предлагаемая тема — минимальный Portable Foundation. Сначала определяем полезный ежедневный сценарий и проверяем переносимость на двух агентах; затем расширяем систему.

| Вопрос | Результат обсуждения |
|---|---|
| Какую первую инженерную задачу должен облегчить harness? | Один конкретный сценарий с входом, результатом и проверкой |
| Что входит в Phase 1? | Минимальный набор компонентов и явные границы версии |
| Где живут personal и repository настройки? | Правила разрешения конфигурации и конфликтов |
| Как распространяются общие skills и инструкции? | Каноническое расположение, установка, обновление, диагностика drift и удаление интеграции |
| Что обязан поддерживать adapter? | Минимальный Capability Descriptor и поведение при неподдерживаемых функциях |
| Как пользователь вызывает общую операцию? | Небольшой CLI-контракт с понятными результатами и ошибками |
| Как проверить переносимость? | Один и тот же сценарий в Codex, Claude и напрямую через CLI |

Выбор языка и packaging следует за этими требованиями. MCP, controller и сервисное развёртывание обсуждаются при появлении сценария, которому они нужны.

## Следующие темы

1. **Контракты и provenance.** Минимальные Task Contract, Run Record, Artifact Manifest и Evaluation Result; идентичность кода и данных, версии схем, связь evidence с конкретным результатом.
2. **Независимая проверка.** Кто задаёт критерии принятия, где исполняется evaluator, кто может изменять evidence и как аннулируется verified-статус после изменения входов.
3. **Applied ML.** Один remote job, переживающий закрытие сессии; фиксация окружения и данных, получение результатов, ограничения ресурсов и численные допуски.
4. **Знания.** Типы записей, scopes, пересмотр утверждений и правила доступа при retrieval.
5. **Оценка harness.** Базовая линия без расширения, development tasks и отдельная итоговая оценка; затраты времени агента и человека.

## Предлагаемый критерий готовности первого прототипа

- Один канонический skill обнаруживается и используется в двух выбранных агентах без независимых копий предметной логики.
- Одна общая операция вызывается из CLI и из обоих агентов, возвращая согласованный результат.
- Диагностика показывает установленные версии, drift и неподдерживаемые capabilities.
- Установка и удаление интеграции не уничтожают пользовательские настройки.
- Документация явно описывает доступные гарантии interactive mode.

Это предложение для согласования в RFC 002, а не уже принятые acceptance criteria.
