# Scope Guard

Не допускать, чтобы технически корректная операция нарушила актуальное ограничение пользователя. Skill переносим между проектами: он не содержит постоянных запретов на конкретные сервисы, авторов или технологии.

Это инструкция агенту, а не независимый технический запрет. Не обещай гарантированного запуска skill или безошибочной интерпретации. Для обязательной блокировки операций см. [границу исполнения](references/enforcement.md), только если задача требует её проектирования или оценки.

## Собери актуальные основания

Перед затронутым изменением сопоставь текущий запрос с предыдущими разрешениями, новыми ограничениями и инструкциями проекта. Используй уже доступный контекст и целевые чтения; не перечитывай всю историю без необходимости.

Различай:
- прямое указание пользователя;
- наблюдаемый факт о системе, с источником и временем/версией;
- собственную интерпретацию или предположение.

Разрешение сохраняется между ходами, пока пользователь его не ограничил или не изменил. Новая оговорка изменяет область прежнего разрешения; общий призыв «продолжай», целевое число или старый план сами по себе не снимают конкретный запрет. Если пользователь прямо разрешил исключение, применяй его в указанном объёме без повторного согласования. Соблюдай иерархию инструкций.

Не выдавай собственный план, текст обоснования в запросе к инструменту, успешную проверку квоты, наличие прав или одобрение общего риска за доказательство разрешения пользователя на конкретный объект.

## Сохрани смысл исключения

Условие «не трогать то, что менял коллега» сохраняй как условие. Список найденных объектов — результат проверки на конкретный момент, а не замена исходного условия. Учитывай точную формулировку пользователя: не расширяй и не сужай её самовольно.

Проверяй кандидатов на изменение по журналу, конфигурациям или другому подходящему источнику. Не считать отсутствие найденного события доказательством отсутствия изменений, если история неполная. Не считать флаг «только сохранено», отсутствие деплоя или отсутствие изменения ресурсов доказательством, что защищаемых изменений нет.

Для каждого кандидата определи статус:
- **Разрешён:** действие входит в актуальное поручение, применимые исключения проверены.
- **Исключён:** действие противоречит актуальному ограничению.
- **Не установлено:** не хватает фактов или есть неразрешённое противоречие в области разрешения.

Сначала получи недостающие факты доступными чтениями. Если неопределённость остаётся, не выполняй зависимое изменение этого объекта. Продолжай независимую разрешённую работу. Задавай пользователю только вопрос, который действительно меняет решение; укажи конкретную неопределённость. Это не повод заново согласовывать весь план.

## Свяжи решение с операцией

Для длительной работы, передачи между сессиями или нескольких объектов сохрани краткую запись в принятом проектом месте. Для простой операции достаточно явного решения в текущем контексте. Не создавай новую систему учёта или общую межпроектную память автоматически.

Минимальные поля записи:

| Поле | Содержание |
| --- | --- |
| Объект | Канонический ID и среда; раскрыть неоднозначные алиасы |
| Действие | Что конкретно изменится, значения до/после, затрагиваемые зависимости |
| Основание | Сообщение/решение пользователя, его порядок или дата |
| Ограничения | Исходный смысл условия и ссылки на применимые правила |
| Проверка | Факты, источник, версия/время и оставшиеся неизвестные |
| Решение | Разрешён / исключён / не установлено, с причиной |

Храни факты и решения отдельно. Не переносить запреты одного проекта в другой. Проектные файлы и память помогают восстановить контекст, но не заменяют более новое прямое указание пользователя.

## Перепроверь перед изменением

1. После нового сообщения, возобновления работы или изменения внешнего состояния пересмотри затронутые решения. Не продолжай старую очередь вслепую. При новом запрете прекрати отправлять затронутые операции; для уже отправленной проверь состояние и безопасную возможность остановки, не делай автоматический откат.
2. Сопоставь реальный payload со статусом объекта и разрешённым действием. Проверь, что общие настройки, селекторы, родительские объекты или массовая операция не затрагивают исключённые объекты косвенно.
3. Учти последствия: перезапуск, загрузку сохранённого конфига, миграцию, распространение общих настроек. «Файл не редактировался» не доказывает, что поведение осталось прежним.
4. Сверь существенные версии и состояние с основанием плана. При расхождении обнови оценку; не подгоняй ожидаемые значения, чтобы проверка прошла. Если API поддерживает атомарные предусловия, используй их. Иначе явно учитывай оставшееся окно гонки.
5. Исполняй только разрешённую часть. Соблюдай существующие права и обязательные согласования; skill сам не даёт новых полномочий и не требует дополнительных согласований для уже разрешённых действий.

Список ALLOWED, составленный самим агентом, проверяет согласованность исполнения с его планом, но не правильность интерпретации поручения. Не называй такую проверку независимой.

## Заверши и сохрани ограничения

Проверь результат и существенные побочные эффекты в масштабе операции. Отделяй «запрос принят», «операция завершена» и «результат проверен». Не утверждай, что защищённое состояние сохранено, по одному косвенному признаку.

При ошибке сначала останови последующие затронутые действия и установи фактическое состояние. Исправление должно учитывать новые изменения других людей; не восстанавливай старый снимок целиком без основания. Используй уже данное разрешение на восстановление, а если его нет — выясни допустимое исправление.

Одноразовое разрешение на восстановление после выполнения не становится постоянным разрешением на будущие изменения. Запиши итог и действующие ограничения в проектном месте, если работа будет продолжаться. В ответе кратко укажи выполненное, исключённое и действительно нерешённое; не перечисляй пустые категории.
