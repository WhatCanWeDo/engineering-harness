Собери пакет для конкретной роли

Учебный пример TTL-кэша. Меняй получателя и бюджет: состав пакета и причины исключения обновятся. Это синтетические записи, не настоящая выдача RAG.

Размеры здесь условные оценки для демонстрации. В системе нужен tokenizer потребителя; обязательный task contract загружается отдельно.

Решения об отборе

    Что увидит агент

      Источники сохраняют revision и область применимости. Рабочий transcript Scout сюда не входит.

      В учебной схеме показаны классы исключений. Настоящий API не должен раскрывать названия или количество найденных private-материалов. Для private-тестировщика нужен отдельный защищённый контур.

      Как результат превращается в знание

      1. 01 · НАДЁЖНО ЗАПИСАТЬOutcome + outboxЗадача и событие в одной транзакции
      2. 02 · ПРЕДЛОЖИТЬCurator + gateИсточники, дубликаты, scope и base revision
      3. 03 · ОПУБЛИКОВАТЬ ИТОГ

      Active означает пригодность записи в её заявленных условиях, а не доказательство универсального правила. Curator не меняет skills и policies автоматически.

      Технические контракты и важные ограничения
      KnowledgeEntry
      ID/revision, kind/state, claim, scope/ACL, applies_to, evidence, origin task/role, observed_at, recorded_at, last_checked_at, supersedes.
      ContextPacket
      Task/spec и knowledge snapshot, audience/stage, claims и citations, caveats/conflicts, бюджет и метод подсчёта, что не поместилось.
      KnowledgeProposal → CommitReceipt
      Изменения и expected_base_revision, ключ повторяемости, записанные revisions, pending approvals, состояние индексов.

      Canonical записи и FTS публикуются в одной транзакции. Vector index догоняет через outbox; перед выдачей права, состояние и revisions проверяются по canonical store.

      Ключ кэша включает права, проект, роль, стадию, task/spec, knowledge snapshot, бюджет и версии моделей/индексов. Отзыв прав инвалидирует выдачу; уже прочитанный LLM контекст задним числом не отзывается.

      SQLite WAL рассчитан на один host и одного writer в момент времени. Живую БД не синхронизируем как файл через облачный диск. Backup/export — отдельная операция; многомашинный endpoint появится при необходимости.

      Общие filesystem-права позволяют обойти логический API. До отдельной OS/service границы нельзя заявлять защиту private-данных. Текст в памяти остаётся данными: он не выдаёт разрешений и не переопределяет инструкции.

      Запись со спорным scope не переносится между проектами автоматически. Для general-записи нужен разрешённый источник или публичная проекция evidence; приватный source path тоже может раскрыть детали.

      Предлагаемый API и порядок реализации

      Команды — часть дизайна; сейчас в проекте их нет.

      harness task begin --contract task.json
harness context prepare --task T --audience developer --budget 1200
harness context expand --packet P --entry K@revision
harness knowledge search --query "TTL expiry" --task T
harness task finish --task T --outcome outcome.json
harness knowledge review --proposal ID
harness knowledge reconcile

      Audience выбирает форму в пределах доверенного task binding, а не расширяет доступ. CLI и MCP используют одно ядро. Native adapters запускают отдельные Scout/Curator и доставляют артефакты.

      Вместо обязательного daemon MVP может обрабатывать очередь на finish, следующем begin и через reconcile. Для свободных разговоров native-сессии полнота lifecycle зависит от интеграции и честно показывается как ограничение.

      Что проверять до использования на реальных проектах
      • Разделение проектов, прав, private данных и стадий initial tests.
      • Конфликт записей, изменение spec/environment, stale и revoked источники.
      • Сбой после queued, повтор обработки, параллельные revisions и потеря доступа.
      • Отставший vector index, невозможность вместить обязательный контекст, отсутствие Scout.
      • Точность citations и полезность пакета по сравнению с no-memory baseline.

      Это план будущих испытаний подсистемы. Проверка интерактивного документа подтверждает только его работу, а не готовность Knowledge Core.

      На что опирается выбор

      Полнотекстовый поиск, BM25 и ограничения tokenizer: SQLite FTS5. Конкурентный доступ и граница одного host: SQLite WAL. Объединение lexical/semantic выдач по рангам: Hybrid search / RRF.
