# Spec Init

Результат — проверяемое понимание задачи: канонический `spec.json`, производные `SPEC.md`, `review.html` и manifest с digest. Прочитай [формат и критерии наполнения](references/format.md). Обоснование выбора формата и первичные источники — [research.md](references/research.md); повторный web research нужен для предметных неизвестных, а не для выбора шаблона при каждом вызове.

## Контекст и первый черновик

1. Сохрани исходное описание пользователя без смысловых правок. Прочитай обязательные project instructions напрямую. Определи project_id и root по текущему проекту; база соседнего проекта не заменяет отсутствующую. Не создавай новую базу и не сканируй HOME ради спеки. Если проект не инициализирован, явно укажи это; существующий legacy store допустим только при известном project_id.
2. Используй доступный [knowledge-cycle](../knowledge-cycle/SKILL.md): `workflow start` с отдельным task_id для **подготовки спеки**, roles:["developer"] и известными paths. Свежий отдельный Scout получает только brief и исходное описание; выбирает refs, может уточнить подпроекты. Затем `workflow context` собирает короткий packet (ориентир 1200 tokens). Этот task_id не переиспользуется как новая реализация. Не передавай весь корпус в основной контекст. В Claude используй non-fork harness-knowledge-worker; в Codex — свежий агент без истории.
3. Запиши в scouting status/task_id/packet_id и сведения о полноте. При пустой выдаче — empty; при недоступности Scout/БД — unavailable с причиной. Можно продолжить черновик с явно отмеченной потерей контекста, но не имитировать выполненную разведку. Убедись, что использованные KB refs входят в packet; сохрани snapshot, scope, state и caveats. Карта кода — подсказка для навигации, не доказательство поведения сервиса. Перепроверь только важные найденные пути/контракты; не перечитывай весь проект. Private evaluation materials не извлекай.
4. **Сначала собери черновик с пробелами.** Для каждого пробела укажи: чего не хватает, как агент временно разрешил вопрос (или почему оставил открытым), основание выбора, последствия ошибки, блокирует ли реализацию и что нужно подтвердить. Предложенный выбор остаётся `proposal`; неизвестный численный порог — `unknown`, а не придуманное требование. Противоречия между запросом и памятью покажи явно; память не переопределяет пользователя.

## Подготовка документов

5. Создай skeleton: `python3 <skill>/scripts/spec.py scaffold --request REQUEST.txt --project PROJECT_ID --id SPEC_ID --title TITLE --output draft.json`. Заполни фиксированные 12 разделов, requirements/acceptance, источники, gaps, task-specific diagram и quiz. Skeleton не является готовой спекой; `validate` проверяет структуру. Для ML-задач явно опиши data/splits/leakage, baseline, метрики/slices, неопределённость измерений, compute budget и воспроизводимость. Для неприменимых частей используй not_applicable с причиной. Подробность масштабируется с задачей, разделы не исчезают.
6. Требование имеет стабильный ID и происхождение. Каждое проверяемое требование связано хотя бы с одним критерием приёмки: что измеряем, метод/данные, порог или явная неизвестность, требуемый artifact. Исследовательский результат может быть отрицательным; обещание улучшения модели не подменяет корректный протокол эксперимента. Acceptance protocol описывается сейчас, тесты не генерируются и не запускаются автоматически. Передай его test-on-request, только когда пользователь попросит тестирование.
7. HTML автоматически собирает замечания и отметки в отдельный текстовый блок с кнопкой «Скопировать»; скачивание TXT не используется. При недоступности clipboard текст выделяется для ручного копирования. HTML объясняет **саму поставленную задачу**: что будет на входе и выходе, путь пользователя, общую систему и место изменения, выбранный подход и альтернативы. Не заменяй это схемой работы spec-init. Различай existing/proposed/external узлы и подпиши направленные связи. Сначала визуальный обзор, затем заметный список пробелов и временных решений, затем подробности. Renderer строит граф из nodes/edges; подписи связей даны в нумерованной легенде. Клик по узлу выделяет его связи. Для большой системы раздели на 2 схемы.
8. Сохрани пять вопросов на понимание из understand-changes: 4 варианта, один ответ по явно описанному черновику, немедленная обратная связь. Не превращай спорный выбор или вопрос к заказчику в тест с «правильным» ответом. Соблюдай [quiz-quality](../understand-changes/references/quiz-quality.md). Quiz и локальные отметки review не являются согласованием спеки. Вопросы для принятия решения находятся в gaps отдельно.
9. Запусти `python3 <skill>/scripts/spec.py build draft.json --packet PACKET.json --output NEW_REVISION_DIRECTORY`. Для unavailable packet не передаётся. Для правки только вёрстки используй `--quiz-from PREVIOUS/review.html`: порядок ответов сохранится. Не правь производные MD/HTML: новая правка → spec.json revision+1 → новый каталог. Скрипт проверяет ссылки и ограничения, экранирует текст, использует общий quiz renderer и отказывается перезаписывать каталог. Посмотри HTML на широком/узком экране и проверь quiz/сборку и копирование замечаний. Отчёт `validation` — проверка структуры, не доказательство полноты постановки.

## Обсуждение и передача

10. Выдай проверенную HTTP-ссылку через [delivery](../understand-changes/references/delivery.md). Кратко подчеркни главные пробелы и свои временные решения, затем задай до трёх самых важных вопросов. При ответах сохраняй ID требований, новую revision и изменения понимания. Не объявляй пробел закрытым только потому, что предложил default. Подтверждённый ответ переносится в user_statement с источником; запись gap сохраняет историю решения.
11. Заверши knowledge-cycle реальным outcome **«черновик спецификации подготовлен»** и дай свежему Curator evidence. Не сохраняй запланированное поведение системы как уже реализованный факт. Не запускай реализацию: назначение этого skill — дать человеку проверить постановку. Согласование фиксируется явным ответом пользователя, привязанным к spec ID/revision/digest; локальный HTML не отправляет решения агенту. При передаче следующему исполнителю укажи этот ответ и точную ревизию, открытые риски и отдельный task_id. Если запрос уже явно содержит разрешение реализовать после согласования, продолжай после такого ответа в его рамках.

## Зависимости и пределы

Python 3.11+, соседние skills knowledge-cycle и understand-changes из этой установки harness. Не копируй их бизнес-логику. Без knowledge runtime подготовь только явно degraded draft; без renderer заверши с конкретной ошибкой, не объявляя HTML готовым. Shared scripts не требуют новой модели, сети или daemon. Native adapters — указатели на этот файл; discovery в новой сессии не равнозначен проверке поведения всех агентов.
