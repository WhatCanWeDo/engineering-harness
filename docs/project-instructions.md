# Общие инструкции проекта

## Контекст

Мы проектируем персональную Native-First, Agent-Agnostic Engineering Harness для applied ML. Начни с `README.md` и RFC 001 в `docs/rfcs/`. Текущую повестку смотри в `docs/design-plan.md`.

Общение и проектная документация — преимущественно на русском; технические названия и идентификаторы могут быть на английском.

## Проектирование

- Сохраняй нативные интерфейсы агентов и переносимое ядро. Предметная логика не должна зависеть от внутреннего формата сессий конкретного агента.
- Различай исходные требования, предлагаемые решения и принятые решения. RFC 001 пока имеет статус Draft v0.1.
- Проектируй минимальный полезный сквозной сценарий перед добавлением абстракций. Не считай все подсистемы RFC обязательными компонентами первой реализации.
- Рассматривай CLI как общий интерфейс, MCP — как опциональный адаптер к той же реализации.
- Разделяй исполнение, evidence и принятие результата. Окончание агентской сессии само по себе не подтверждает корректность.
- Различай advisory checks и enforceable gates. Инструкции, hooks и локальный файл статуса сами по себе не обеспечивают изоляцию или независимость проверки.
- При описании поддержки конкретного агента проверяй актуальную официальную документацию и фиксируй версию или дату проверки. Ссылки исходного RFC не являются готовой матрицей совместимости.
- Не превращай гипотезы о внешнем tooling в зависимости проекта до их проверки.

## Документация и изменения

- Канонический текст общих инструкций находится в этом файле. `AGENTS.md` и `CLAUDE.md` служат тонкими входными указателями и не дублируют правила.
- Архитектурные документы хранятся в репозитории. Существенные изменения оформляй отдельным RFC или явно обновляй версию существующего документа.
- Не меняй статус Draft на Accepted без явного решения пользователя.
- Фиксируй открытые вопросы и ограничения рядом с затронутым решением.
- Для изменений документации проверяй ссылки, структуру и согласованность статусов. Для будущего кода выбирай проверки по его поведению и рискам.

## Цикл знаний в этом проекте

Для новых инженерных задач включён [knowledge-cycle](../skills/knowledge-cycle/SKILL.md), project_id `engineering-harness`. Перед задачей отдельный свежий Scout выбирает контекст; после реального outcome отдельный свежий Curator предлагает evidence-backed знания. Используй готовый CLI workflow вместо ручной сборки prompt/очереди/пакетов. Подробности генерации тестов остаются в отдельных тестовых агентах. Сам цикл знаний не включает тестирование без запроса пользователя. Shared general публикации и спорные обобщения требуют решения пользователя; кандидаты сохраняются автоматически.
