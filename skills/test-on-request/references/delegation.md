# Генерация тестов в отдельном агенте

Обязательное пользовательское требование: public, private и adversarial тесты генерируются вне контекста разработчика. Цель — не загружать разработчика деталями генерации и отладки тестов. Это отдельная гарантия от секретности private suite.

## Вход генератора

Передавай компактный task brief:

- task ID, тип тестов, spec version, открытые требования и oracle policy;
- интерфейсы и конкретные разрешённые файлы/артефакты;
- фазу разработки и candidate ref только там, где он допустим;
- разрешённый output scope, команды проверки и лимиты ресурсов;
- формат возвращаемого результата и политику раскрытия.

Не наследуй автоматически историю разработчика, его промежуточные решения, гипотезы о багах и незавершённые варианты реализации. Не передавай заранее ожидаемый вывод adversarial-поиска. Если контракта недостаточно, генератор возвращает точный вопрос/requirement ID, а не запрашивает всю историю. Вопросы, влияющие на поведение продукта, должны дойти до пользователя или разработчика; их нельзя скрывать вместе с рабочими логами.

## Разделение ролей

| Генератор | Что получает | Что возвращает разработчику |
|---|---|---|
| Public | Контракт, интерфейс, разрешённый baseline до целевого изменения | Готовые тестовые файлы/patch, краткую матрицу требований, команду запуска и результат проверки самих тестов |
| Private | Контракт и разрешённые интерфейсы внутри защищённой среды | Только opaque suite reference, квитанцию подготовки и разрешённый summary; содержимое остаётся у evaluator |
| Adversarial | Публичный контракт, frozen candidate, бюджет | Подтверждённые findings, минимальные reproducers, готовые regression-тесты и краткие ограничения поиска |

Используй отдельные новые worker-контексты для этих ролей. Private-автор не переходит в роль разработчика или автора публичного объяснения. Генератор public не должен получать private package. Внутри одного назначения генератор может продолжать свою сессию для отладки тестов; это не повод возвращать её историю разработчику.

## Обратная передача

Обычный ответ генератора — короткое структурированное резюме: `status`, `task_id`, `spec_version`, `candidate_ref` при наличии, пути готовых разрешённых артефактов, команда воспроизведения, фактически выполненные проверки, блокирующие вопросы и ограничения. Не возвращай черновики, весь ход перебора случаев и полные логи в родительский диалог.

Разработчик вправе читать финальные public tests и разрешённые reproducers — это полезная часть контракта. Сокращение контекста касается процесса генерации, а не сокрытия результата или существенных ограничений. Для исправления дефекта передавай expected/actual behavior, requirement ID и минимальный reproducer; подробности отладки тестового инструмента обычно не нужны.

Генератор пишет только в выделенный scope тестов/артефактов, не меняет продукт и критерии принятия ради прохождения. Замеченную проблему контракта возвращает как вопрос. Выполнять готовые public tests может обычный runner или разработчик, если это разрешено: требование другого агента относится к генерации. Создание regression-теста по раскрытому private-примеру также поручается public-генератору с доступом только к уже разрешённому примеру.

## Ограничения среды

Adapter должен уметь создавать отдельный контекст, передавать минимальные входы и получать ограниченный итог. Если инструмент автоматически прикладывает полную историю либо возвращает весь worker transcript, нельзя обещать изоляцию контекста без соответствующей настройки. При отсутствии нужной возможности — `generation_unavailable` и brief для отдельной сессии; локальная генерация разработчиком не является эквивалентной заменой.

Обычные subagents с общим filesystem подходят для отделения public/adversarial генерации от рабочего контекста. Они не обеспечивают приватность: shared files, tool outputs, transcript storage и retrieval должны быть защищены отдельно для private-роли. Это описано в [private-evaluation.md](private-evaluation.md).
