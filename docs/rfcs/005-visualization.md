# RFC 005 — Visualization: интерактивное представление результата

**Status:** Draft v0.1 · **Date:** 2026-11-06

## Решение, которое предлагается

`visualization` — переносимый skill-роутер с набором специализированных мини-workflows. Он помогает увидеть фактический результат работы и исследовать его через подходящее взаимодействие. Сначала показывается предмет задачи: изображение и маска, страница и извлечённые поля, запрос и найденные документы. Архитектурная схема дополняет это, если помогает ответить на вопрос пользователя.

Первоначальный результат RFC — дизайн и два интерактивных прототипа в HTML. На 2026-11-06 добавлен устанавливаемый instruction-based MVP `skills/visualization`: router, три recipes, общие проверки и переиспользование HTML preview. Установщик подключает advisory правило предложения после задач. Универсальный renderer и live ML backend пока не реализованы; HTML для конкретной задачи создаёт агент по выбранному recipe.

## Пользовательский сценарий

1. Агент завершает основную задачу и сохраняет реальные outputs/evidence. Частичный или неудачный результат также может быть полезно визуализировать; его статус не меняется.
2. Короткая проверка применимости: есть ли вопрос, на который визуальная форма отвечает лучше текста? Примеры: где модель ошибается, какой узел страницы дал значение, чем отличаются до/после. Для простой правки одной строки предложение обычно не нужно.
3. Один раз в конце задачи агент предлагает **конкретную** визуализацию: «Могу показать входной кадр и маску рядом, с выбором примера и прозрачностью. Использую сохранённые результаты; нового inference не будет». При существенных затратах/доступах указывает их и отдельно ограничивает scope. Основная работа уже завершена; согласие на визуализацию не требуется для выдачи её результата.
4. При согласии агент вызывает visualization, выбирает нужный мини-workflow, собирает артефакты и создаёт HTML. Явное «сделай демо» уже является согласием; повторный вопрос не нужен. Отказ относится к предложению этой задачи, без повторных напоминаний. Если пользователь просит делать всегда, настройка может быть явно сохранена для выбранного scope.
5. Агент проверяет соответствие демо артефактам и работу контролов, выдаёт проверенную кликабельную ссылку. Просмотр не означает успешное прохождение evals.

Пользователь выбрал default при отсутствии данных: показать доступное, перечислить пробелы и предложить отдельный прогон. **Недостающие реальные результаты не заменяются выдуманными.** Учебная иллюстрация возможна по отдельному запросу и всегда отделена от результата задачи. Прототипы этого дизайна показывают идею интерфейса на учебных fixtures; не являются результатами сегментационной модели или production-парсера.

## Набор мини-workflows

Мини-workflow — лениво загружаемые инструкции, контракт входных артефактов, шаблон взаимодействия и проверки. Не новая агентская сессия и не обязательный дополнительный LLM-вызов. Общие правила происхождения данных и выдачи находятся только в роутере. Если модуль позже станет полезен отдельно, его можно вынести в отдельный skill с тем же контрактом.

| Модуль | Вопрос пользователя | Основная интерактивность | Нужные реальные данные |
|---|---|---|---|
| image-result | Что модель увидела и где ошиблась? | input/output рядом, overlay, синхронный zoom/pan, выбор sample/frame/class | source, prediction, геометрия preprocessing, class map, run/config; GT только если есть |
| extraction-trace | Откуда взялось это поле? | click output → source highlight → selector/matches → raw → transform → output | snapshot DOM/response, extraction trace, node/span refs, transforms/errors |
| record-flow | Как преобразилась запись? | один record по стадиям, before/after, причины drop/reject | вход/выход каждого доступного шага, record identity и lineage |
| ranking-inspector | Почему эти результаты оказались выше? | запрос, кандидаты, ranks/scores, фильтры и reranking | зафиксированный query/corpus, ranks/scores/filters; score не объявляется probability |
| metric-comparison | Где стало лучше и какой ценой? | baseline/candidate, slices, distributions, uncertainty, sample drilldown | сопоставимые runs, sample IDs, metric definitions, hardware/budget |
| behavior-playground | Что произойдёт при таком вводе? | ввод/событие → реальная функция или зафиксированный replay → состояние/вывод | callable разрешённого исполнения либо трасса с versioned inputs/outputs |

MVP: image-result + extraction-trace и общий каркас. Остальные модули — расширения каталога. Не подключать шесть независимых frameworks ради шести представлений.

## Место в harness

Native agent → завершённая задача + evidence → конкретное предложение → согласие → visualization router → выбранный recipe + artifact pack → проверенный viewer → пользователь.

- `knowledge-cycle` помогает найти полезный контекст; истины об outputs берутся из артефактов текущего run, не из похожей записи памяти.
- `spec-init` до выполнения фиксирует, что человек хочет увидеть. Design mockup заранее остаётся mockup; не становится результатом выполнения.
- `understand-changes` объясняет смысл изменений и даёт quiz. Visualization показывает наблюдаемое поведение; standalone демо не обязано иметь quiz. В составе учебного объяснения используются прежние пять вопросов.
- Простая карта целой системы сохраняется, когда без неё непонятны границы. Её можно поместить рядом/ниже предметного демо; запретить заменять требуемое демо большим графом компонентов.
- `test-on-request` проверяет результат по запросу. Выбор красивого примера не меняет gate verdict.
- `harness-ab` позже сравнит варианты представления по точности понимания и времени review. Значимость эффекта нельзя заявлять по одному удачному просмотру.

Предложения после задач в native-first режиме обеспечиваются коротким правилом project instructions с двумя действиями: оценить применимость и предложить. Сам skill не может включать себя после каждой сессии. Это advisory дисциплина, не гарантированный lifecycle hook; отказоустойчивый controller не добавляется. Установщик подключает это правило через managed block и `docs/installation-profile.md`.

## Контракт данных и честности

Предлагается `view.json` v1 как единый источник конфигурации и метаданных. Минимальный состав:

- `task_id`, `project_id`, `view_id`, `recipe`, `question`, `result_status` (complete/partial/failed).
- `mode`: **recorded** — просмотр сохранённого результата; **executed** — реальный вызов обработчика с указанной реализацией; **illustrative** — учебная сцена/симуляция, не evidence задачи. Метка видна над панелью, а не только в footnote. Смешанные панели имеют отдельные метки; не соединяются как input/output одного run.
- `artifacts[]`: ID, роль, local URI, digest, media/schema type, sample/frame identity, capture/run metadata, redactions. Для больших данных — bounded subset с объяснением отбора.
- `claims[]`: показываемое утверждение, artifact refs, limits. Пустая ссылка или отсутствующий файл не заменяются правдоподобным значением.
- `bindings`: пары input/output, координаты и transformations; для extraction — output field ↔ source node/span ↔ transform trace. Несогласованная пара не показывается как реальная связь.
- `controls[]`: действие пользователя, тип **display**, **replay-selection** либо **execute**, доступный диапазон и что именно меняется. display не переписывает predicted mask или metrics; replay не выдаётся за новый расчёт.
- `sampling`: общий объём, выбранный subset, правило отбора, исключения и пределы репрезентативности.
- `missing[]`: чего нет, какую часть демо это ограничивает, что потребуется для получения. `proposed_runs[]` остаются предложениями, не запускаются при открытии страницы.
- `checks`: provenance/bindings, correctness of displayed transforms, controls, browser layout. Отличать passed/failed/not_run.

Факты и configs сериализуются скриптами из реальных artifacts. LLM выбирает вопрос/формат и пишет объяснение; не рисует результаты модели или extraction traces из воображения. Повторяемые проверки, пакетирование и отрисовка не требуют дополнительных agent calls.

## Image-result: сегментация

Слева — исходный кадр, справа — prediction. Можно включить overlay, выбрать класс, сменить sample; zoom/pan связан между панелями. Видны sample/frame ID и режим recorded/live. Если есть GT, она показывается отдельно от prediction, доступны error overlay и метрики с областью расчёта. Если GT отсутствует — это явно написано, accuracy/IoU не выдумываются.

Нужны исходные размеры, crop/resize/letterbox и обратное преобразование координат. Категориальные маски нельзя сглаживать так, чтобы появлялись несуществующие class IDs. Одинаковый class map и цвета сохраняются между кадрами. Прозрачность и zoom меняют отображение; вывод модели остаётся тем же. Порог confidence показывается только при наличии соответствующих вероятностей и воспроизводимого postprocessing. Сохранённая последовательность кадров называется replay; FPS плеера не называется скоростью модели. Согласие на viewer само по себе не включает камеру и не запускает дорогой GPU inference.

## Extraction-trace: парсер

Три связанные области: представление исходника, путь извлечения, итоговые поля. Выбор поля подсвечивает точный source node/span, показывает selector/path, число matches, raw value, все существенные преобразования и output. Например `"12 490 ₽" → remove grouping/currency → 12490 RUB`. При 0 matches показывается missing; при нескольких matches — неоднозначность или фактическое правило выбора. Не подставлять старый output после изменения source.

Снимок сайта должен относиться к тому же документу, на котором выполнялось извлечение. Для JS-сайта distinction raw response / rendered DOM обязателен. Копия интерфейса и реальный screenshot различаются; если оригинальной геометрии нет, можно показать DOM/text snapshot вместо вымышленной подсветки на живом сайте. Если trace отсутствует, предложить replay настоящего extractor на snapshot; повторная иллюстративная реализация в JS не считается трассой production кода.

Сторонний HTML — недоверенные данные: scripts/handlers/network/секреты не переносятся в исполняемую страницу. По умолчанию inert/sanitized representation, сохранённые source identity и redaction map. При удалении элементов нельзя незаметно менять отображаемую связь с исходным trace. Изолированный live backend — отдельный optional слой, не скрытый сетевой fetch из автономного демо.

## Красота и понятность

Предметный результат занимает центр экрана. Один главный вопрос на экран, исходник и результат одинакового масштаба, несколько полезных controls вместо панели десятков переключателей. Настройки с большим влиянием раскрываются постепенно. Цвет имеет устойчивый смысл и текстовую легенду; сравнения используют одинаковые единицы/оси/масштабы. Плохие/пограничные примеры доступны вместе с успешными, правило отбора видно.

Клавиатура и touch поддерживаются; смысл не зависит только от hover или цвета. На узком экране пары складываются вертикально с сохранением выбранного sample и доступным переключением input/output. Auto-play и постоянное движение не обязательны. Формальные научные графики для экспорта остаются отдельным статическим артефактом; интерактивность не самоцель.

## Предлагаемая структура

```text
skills/visualization/
  SKILL.md                 # offer/consent, router, честность, выдача
  references/
    artifact-contract.md
    review-checks.md
  recipes/
    image-result.md        # сценарий + contract + fidelity checks
    extraction-trace.md
    ...                    # только по мере появления задач
  scripts/
    inspect_artifacts.py   # inventory/IDs/digests/dimensions — без модели
    validate_view.py       # refs, pairing, missing, control types
    build_view.py          # общий shell + выбранный renderer
  assets/
    shell/                 # layout, provenance labels, controls, notes
    image-result/
    extraction-trace/
```

Это предлагаемые компоненты, не существующие команды. Существующие delivery/preview и quiz переиспользуются; remarks в HTML собираются в копируемый текстовый блок, без TXT downloads. Большие assets могут потребовать отдельного loopback viewer с allowlisted файлами: текущий preview обслуживает один HTML. MVP вкладывает небольшой выбранный набор в standalone HTML; видео/большие datasets не обещает поддерживать без расширения доставки.

## Минимальный путь реализации и критерии приёмки

1. Router и правило предложения после задачи; пользователь видит конкретную пользу и тип имеющихся данных. Отказ не запускает viewer/дополнительные работы, согласие не спрашивается повторно.
2. Контракт + exporter для имеющихся artifacts; missing/mismatched pairs видны до рендера. Integrity проверки не равны доказательству семантической правильности данных.
3. Image-result и extraction-trace на реальных fixtures с известным происхождением. Чётко отличать тестовый fixture от результата пользовательской задачи. Удалённый artifact или неправильно спаренный frame должен давать понятную ошибку, а не правдоподобное демо.
4. Проверка взаимодействий и fidelity: controls отражают заявленный эффект, показанные transforms совпадают с trace, нет незаявленного rerun/network/camera. Browser checks на широком/узком экране; фактический content readable.
5. Пилот на реальной задаче: пользователь может по демо верно указать, что сделано, какой источник дал результат и чего вывод не доказывает. Запись caveats, времени review и исправлений; A/B — отдельно по запросу.

Главный критерий: визуализация позволяет сделать **правильный вывод о реальном результате**, а не просто убедительно выглядит.
