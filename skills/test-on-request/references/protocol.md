# Протокол тестирования по запросу

Дизайн v0.2, 2026-11-03. Публичность и время создания — независимые характеристики теста. `origin` сохраняется после раскрытия: ранее приватный тест становится публичным, но его происхождение не переписывается. Все тесты генерирует отдельный агент по [контракту делегирования](delegation.md); разработчик получает готовые разрешённые результаты без истории их генерации.

## Открытый контракт

До initial suite зафиксировать:

- `task_id`, `spec_version`, требования с устойчивыми ID, допустимые входы, ошибки, tolerances и ограничения.
- Операцию и выбранные типы тестов; «полный цикл» — явное включение всех трёх.
- Кто создаёт/исполняет проверки, какая модель угроз и какие данные доступны каждому участнику.
- Политику oracle: спецификация, проверенная простая реализация или допустимые свойства. Совпадение двух реализаций само по себе не доказывает правильность; metamorphic relation требует обоснования из контракта.
- Ограничения времени, ресурсов и числа обращений к evaluator. Это публичные правила, а не скрытые критерии.

Текущая пользовательская политика: при провале private сразу выдаётся минимальный reproducer и становится публичным regression-тестом. Недоступная минимизация не должна скрывать найденный баг: выдать имеющийся воспроизводимый разрешённый пример и указать, что он не минимален.

## Жизненный цикл

1. **Specification fixed.** Уточнён публичный контракт. Изменение существенного требования создаёт новую версию и помечает зависимые результаты устаревшими.
2. **Suites prepared.** Публичный initial suite и приватный пакет созданы до разработки целевого решения. Приватный автор видит контракт и интерфейс, но не будущую реализацию. Для уже существующей системы baseline-код может быть доступен, что явно записывается; тесты тогда независимы лишь от целевого изменения, не от всей реализации.
3. **Development.** Исполнитель видит требования и публичный набор, может запускать разрешённые готовые проверки. Если нужны новые тесты, ставит задачу отдельному public-генератору, а не пишет их в своём рабочем контексте. Полезные проверки не запрещаются ради чистоты benchmark; соблюдаются явный scope пользователя и разделение генерации.
4. **Candidate frozen.** Snapshot включает код, dirty/untracked файлы в scope, конфигурацию и зависимости. Commit ID достаточен только для действительно чистого и воспроизводимого checkout. При необходимости фиксируются data/model/hardware IDs.
5. **Adversarial search.** Атака на конкретный snapshot. После разрешённых исправлений возникает новый snapshot; все доказательства остаются привязанными к исходному.
6. **Private evaluation.** После публичных регрессий и атак оценить final candidate на заранее подготовленном пакете. Этот порядок уменьшает число запросов к holdout; он не меняет требование создать пакет до разработки.
7. **Disclosure and repair.** Минимальный пример раскрывается сразу; disclosure event связывает его с evaluator run и новым публичным regression. После исправления можно повторить оценку в рамках бюджета, но использованный набор уже не свежий.

Adversarial-поиск можно запросить отдельно после уже выполненной private-оценки. Любое последующее изменение кандидата делает прежний результат неприменимым к новой версии. Не возникает автоматической универсальной последовательности для каждой задачи.

## Приватный набор и резерв

До разработки можно выделить working private suite и отдельный reserve. Reserve не используется для выбора исправлений до финального запроса. Обе части проверяют тот же открытый контракт. Это опция для задач, где независимая итоговая оценка оправдывает расходы; не требование создавать большой benchmark для любой функции.

После первого ответа evaluator даже общий pass/fail является обратной связью. Частично раскрытый набор не превращается весь в публичный, но его повторное использование учитывается как адаптивное. Если кейсы одного семейства позволяют восстановить остальные, disclosure event помечает затронутое семейство и reviewer решает, пригодно ли оставшееся для holdout.

Не генерировать «свежий holdout» после просмотра конкретного багфикса и не называть его заранее независимым. Такие тесты — полезные дополнительные post-hoc проверки. Если reserve исчерпан, честно показать `fresh_holdout_available: false`.

## Предлагаемые бюджеты

Параметры выбираются под задачу. Стартовое предложение для небольшой локальной функции: adversarial до 10 минут выполнения проверок, до 1000 сгенерированных случаев и до 5 подтверждённых находок; остановка по первому исчерпанному лимиту. Генерация/анализ моделью учитываются отдельно от времени запуска. Это не SLA и не гарантия поиска всех багов. Seed, размер примера и ограничение ресурсов фиксируются отдельно; время minimization входит в execution budget.

Для private — предложенный максимум 3 обращения на задачу, включая исправления; больше только по явному изменению бюджета. Простой новый candidate ID не обнуляет счётчик. Enforcement находится у evaluator; если лимиты соблюдаются только агентом, это advisory. Для долгих ML/GPU запусков нужны явно заданные лимиты, фиксированные данные/среда и политика повторений при недетерминированности.

## Пакеты результатов

Публичный `TestPlan`:

```json
{
  "version": 1,
  "task_id": "cache-ttl",
  "spec_version": "1",
  "selected_suites": ["public", "private", "adversarial"],
  "feedback": "release_minimal_reproducer",
  "private_suite_ref": "opaque-evaluator-issued-id",
  "private_available": false,
  "candidate_ref": null
}
```

Здесь opaque ID — пример формы, не созданный пакет и не доказательство изоляции. Публичная запись не содержит приватных путей, данных, seeds и expected outputs. Квитанция доверенного evaluator подтверждает версию подготовленного пакета и время sealing; локальный изменяемый manifest исполнителя этого не доказывает.

`EvaluationResult` связывает `run_id`, `task_id`, `spec_version`, `candidate_ref`, suite versions, status каждого набора, environment и evidence. Для поиска отдельно фиксируются бюджет и `no_counterexample_found`/`counterexample_found`. `Freshness` отражает pre/post-hoc происхождение и количество feedback events. Если выбранный private недоступен, общий статус — partial/unavailable, не общий pass.

`Finding` содержит requirement ID, candidate ref, reproducer, ожидаемый/фактический результат, команду воспроизведения, seed/окружение, минимизацию, severity и подтверждение oracle. `DisclosureEvent` сохраняет origin, старую/новую visibility, разрешённые раскрытые данные, evaluator run и ссылку на публичный regression. Полные raw logs защищённой оценки остаются у evaluator; выдача разработчику строится из разрешённых полей.

## Качество тестов

- Матрица requirement → наблюдаемое свойство → oracle → типы случаев. Все обязанности программы открыты.
- Публичные проверки могут быть очень сильными, включать свойства, важные края и даже полный перебор малого конечного домена. Ограничивать их искусственно не нужно.
- Приватные случаи расширяют проверку комбинаций и распределений; нельзя прятать новое требование в expected output.
- Перед использованием evaluator проверь сам oracle на ручных примерах и, где полезно, известных дефектных реализациях. Mutation testing помогает найти слабые assertions, но процент уничтоженных мутаций не является доказательством корректности продукта.
- Adversarial failure требует triage: bug / спорный контракт / ошибка oracle / flaky test / инфраструктура. Изменение теста после обнаружения проблемы создаёт новую версию с причиной; не переписывает историю провала.
- Оптимизируй найденные классы ошибок и время исправления, а не число тестов или строк покрытия.
