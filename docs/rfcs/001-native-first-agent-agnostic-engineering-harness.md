# Native-First, Agent-Agnostic Engineering Harness

**Architecture Design Document — RFC 001**

**Status:** Draft v0.1  
**Date:** 2026-11-03  
**Primary use case:** Personal Applied ML Engineering Environment

---

## 1. Executive Summary

Предлагается создать персональный engineering harness, который расширяет возможности существующих coding agents, сохраняя их нативные интерфейсы и не создавая зависимости от конкретной модели или поставщика.

Основные агенты на первом этапе — Codex CLI и Claude Code. Архитектура должна допускать подключение других агентов без переписывания основной бизнес-логики системы.

Harness предоставляет общую инфраструктуру для:

- Повторно используемых skills и инженерных workflows.
- Независимой проверки результатов работы агентов.
- Воспроизводимых ML-экспериментов и benchmarks.
- Управления контекстом и долговременными знаниями.
- Сбора и представления артефактов работы.
- Контроля разрешений, ресурсов и выполнения quality gates.
- Оценки эффективности самого harness.

**Ключевое архитектурное решение:** не разрабатывать собственный agent loop. Использовать готовые coding agents как execution environments, а общую логику размещать в независимом от них слое.

Система должна поддерживать постепенное развитие: от библиотеки переносимых skills до полноценной orchestration-платформы — без обязательного перехода на неё для повседневной работы.

## 2. Problem Statement

Существующие coding agents предоставляют достаточно качественные механизмы редактирования кода, взаимодействия с терминалом, работы с контекстом и делегирования задач.

Однако при построении персонального инженерного окружения появляются системные проблемы.

**Vendor lock-in.** Инструкции, hooks, настройки, способы делегирования и формат сессий различаются между инструментами. Создание отдельного набора возможностей для каждого агента приводит к дублированию и усложняет миграцию.

**Непроверенные результаты.** Агент способен самостоятельно объявить задачу выполненной, даже когда существенные требования не проверены. Текстовое утверждение об успешности работы не эквивалентно независимому доказательству.

**Слабая воспроизводимость.** Результаты applied ML экспериментов зависят от кода, данных, окружения, модели, hardware и конфигурации. Без общего механизма фиксации этих зависимостей результаты сложно сравнивать и воспроизводить.

**Фрагментированные знания.** Принятые решения, отрицательные результаты и полезные наблюдения могут оставаться в истории конкретной агентской сессии.

**Потеря человеческого понимания.** Ускорение разработки не должно приводить к ситуации, когда разработчик больше не понимает архитектуру, предположения и ограничения реализованных решений.

**Сложность оценки agent tooling.** Добавление новых skills и workflows увеличивает сложность системы, но не гарантирует повышения качества или производительности.

Harness должен решать эти проблемы независимо от конкретного coding agent.

## 3. Goals and Non-Goals

### 3.1 Goals

**G1. Native-first UX**

Разработчик продолжает работать в привычных Codex CLI, Claude Code или другом совместимом инструменте. Harness не требует перехода в отдельный интерфейс.

**G2. Single Source of Truth**

Каждая инструкция, capability, policy и workflow имеет единственное каноническое определение. Agent-specific конфигурации являются производными от него либо тонкими адаптерами.

**G3. Agent Portability**

Переход между агентами не должен требовать переписывания общих skills, evaluators, экспериментальных инструментов или форматов артефактов.

**G4. Independent Verification**

Корректность результатов определяется независимыми проверками и воспроизводимыми артефактами, а не только заключением агента.

**G5. Applied ML Support**

Система должна учитывать удалённые GPU environments, долгие эксперименты, метрики производительности, evaluation datasets, большие артефакты и недетерминированность вычислений.

**G6. Human Understanding**

Архитектура должна поддерживать механизмы объяснения решений, проверки понимания и интерактивного исследования сложных концепций.

**G7. Incremental Adoption**

Компоненты должны быть полезны независимо друг от друга. Первоначальная версия не должна требовать установки полноценного orchestration framework.

**G8. Observability and Measurability**

Работа harness и качество его расширений должны измеряться с помощью воспроизводимых тестов и benchmarks.

### 3.2 Non-Goals

Система не предназначена для:

- Замены Codex, Claude Code или их внутренних agent loops.
- Реализации собственной модели, inference engine или LLM API gateway.
- Унификации всех внутренних событий и особенностей coding agents.
- Гарантирования идентичного поведения разных моделей.
- Создания собственной IDE или терминального интерфейса на начальном этапе.
- Принудительной автоматизации каждой инженерной задачи.
- Замены существующих CI/CD, experiment tracking и infrastructure tooling там, где они уже решают задачу.
- Автоматического предоставления агентам доступа ко всем локальным или корпоративным ресурсам.

## 4. Architectural Principles

### 4.1 Portable Core, Native Edges

Вся предметная логика размещается в общих компонентах.

Agent-specific код ограничивается интеграцией: обнаружением skills, регистрацией инструментов, настройкой permissions и сопоставлением lifecycle events.

### 4.2 Deterministic Core, Probabilistic Assistance

Проверка инвариантов, хранение артефактов, управление ресурсами и принятие обязательных решений должны опираться на детерминированные механизмы там, где это возможно.

LLM применяется для генерации кандидатов, анализа, объяснения и исследовательских действий.

LLM-оценки могут быть частью evidence, но не должны автоматически подменять объективные проверки.

### 4.3 Separation of Execution and Verification

Исполнитель и проверяющий контур имеют разные полномочия.

Агент может изменять проект и запускать разрешённые проверки, но не должен иметь возможность произвольно менять критерии принятия результата или получать защищённые evaluation artifacts.

### 4.4 Explicit Trust Boundaries

Инструкции внутри skill не являются механизмом безопасности.

Если необходимо гарантированное ограничение доступа или выполнения, оно должно обеспечиваться вне agent loop — операционной системой, изолированной средой, независимым сервисом или CI.

### 4.5 Evidence Over Assertions

Результат работы представляется как набор проверяемых утверждений и связанных с ними артефактов.

Статус успешности должен соответствовать действительно выполненным проверкам.

### 4.6 Progressive Complexity

Новые архитектурные компоненты вводятся только тогда, когда существующих механизмов недостаточно или появляется измеримый выигрыш.

## 5. High-Level Architecture

Система разделяется на четыре логических слоя.

### Layer 1 — Native Agent Environments

Пользовательские точки входа:

- Codex CLI.
- Claude Code.
- Другие coding agents, подключаемые в будущем.

Каждый агент сохраняет собственные механизмы работы с моделями, сессиями, контекстом, терминалом и редактированием файлов.

Harness не перехватывает и не заменяет их основной agent loop.

### Layer 2 — Agent Integration Layer

Тонкий слой совместимости, отвечающий за:

- Подключение общих skills.
- Предоставление постоянных project instructions.
- Регистрацию CLI/MCP capabilities.
- Подключение доступных lifecycle hooks.
- Интерпретацию поддерживаемых agent-specific событий.
- Обнаружение возможностей и ограничений агента.

Интеграции не содержат предметной логики skills или evaluators.

Каждый adapter декларирует поддерживаемые возможности. Если определённая функция недоступна у агента, система явно сообщает об ограничении, а не имитирует успешное выполнение.

### Layer 3 — Shared Harness Core

Основные подсистемы:

| Component | Responsibility |
|---|---|
| Skill Registry | Каноническое хранение и обнаружение skills |
| Workflow Definitions | Описание многостадийных инженерных процессов |
| Policy Engine | Проверка правил, ограничений и условий допуска |
| Evaluation System | Независимые проверки качества и корректности |
| Execution Gateway | Доступ к разрешённым локальным и удалённым runners |
| Artifact Registry | Учёт результатов, документов, метрик и экспериментальных outputs |
| Knowledge Store | Хранение подтверждённых знаний, решений и гипотез |
| Capability Registry | Информация о возможностях подключённых агентов |
| Observability Layer | Журналы, диагностика и показатели работы harness |

Все подсистемы предоставляют стабильные интерфейсы, не зависящие от конкретного coding agent.

### Layer 4 — Infrastructure and External Systems

Слой инфраструктуры включает:

- Local development environment.
- Git repositories и worktrees.
- Containers и изолированные execution environments.
- Remote GPU machines и job schedulers.
- CI/CD.
- Object storage и experiment tracking systems.
- Evaluation frameworks.
- Разрешённые внешние сервисы.

Harness координирует обращение к этой инфраструктуре, но не обязан самостоятельно реализовывать каждую её часть.

### Architectural Data Flow

**Interactive path**

User → Native Agent → Shared Skill / CLI / MCP → Harness Core → Execution Infrastructure

**Verification path**

Code / Artifacts → Independent Evaluator → Evidence Records → Acceptance Decision

**Knowledge path**

Verified Results → Knowledge Store → Context Retrieval → Native Agent

**Optional managed path**

User / CI → Workflow Controller → Agent Adapter → Coding Agent → Evaluation and Artifacts

Managed path не является обязательным для повседневных интерактивных сессий.

## 6. Main Subsystems

### 6.1 Skills and Instructions

Skills используют открытый формат Agent Skills, основанный на `SKILL.md`.

Единый каталог выступает источником истины. Agent-specific пути установки, команды и metadata рассматриваются как детали интеграции.

Общие инструкции проекта хранятся независимо от файлов конфигурации конкретных агентов. При необходимости из них формируются `AGENTS.md`, `CLAUDE.md` или соответствующие entrypoints.

При этом архитектура признаёт различия между агентами: формат переносим, но порядок загрузки, автоматическое обнаружение и фактическое применение skill могут отличаться.

### 6.2 Tool and Capability Interface

Операции harness доступны через два основных интерфейса:

**CLI** — универсальная точка входа для человека, coding agents, скриптов и CI.

**MCP** — опциональный интерфейс для структурированного доступа агентов к общим инструментам.

Оба интерфейса обращаются к одной реализации Core API. MCP не должен создавать параллельную бизнес-логику.

Подключение конкретного MCP-сервера не означает автоматического предоставления всех его возможностей каждому агенту.

### 6.3 Workflow Layer

Workflow определяет последовательность этапов, зависимости, ответственность исполнителей, условия завершения и требуемые артефакты.

Он должен различать:

- Agent-executed steps.
- Deterministic execution steps.
- Independent verification steps.
- Human approval steps.

На начальном этапе workflow может реализовываться набором CLI-команд и соглашений.

В будущем допускается отдельный controller, который управляет состоянием, повторными попытками, остановкой и восстановлением выполнения.

Workflow definitions остаются независимыми от конкретного orchestration engine.

### 6.4 Evaluation and Quality Gates

Evaluation subsystem принимает определённый контракт проверки и возвращает структурированный результат.

Проверки могут включать функциональную корректность, регрессии, performance, численные допуски, качество моделей и дополнительные инженерные требования.

Система различает:

- Проверки, доступные исполнителю.
- Независимые проверки в защищённой среде.
- Исследовательские или модельные оценки.
- Формальные условия принятия результата.

Завершение агентской сессии не равнозначно успешному прохождению quality gates.

### 6.5 Execution Infrastructure

Execution Gateway предоставляет единый способ обращения к разрешённым вычислительным средам.

Логически различаются:

- Interactive local execution.
- Isolated evaluation execution.
- Remote/accelerated execution.

Для каждой работы должны быть определены ограничения ресурсов, время жизни, уровень доступа и место хранения результатов.

Долгие GPU jobs не должны зависеть от существования активного разговорного контекста.

### 6.6 Artifact and Evidence Registry

Каждая существенная инженерная операция может создавать versioned artifacts.

Реестр должен связывать результат с контекстом его получения: версией кода, входными данными, конфигурацией, environment и выполненными проверками.

Система должна различать:

- Предположение агента.
- Наблюдение.
- Подтверждённый результат.
- Решение, принятое человеком.

Большие бинарные артефакты могут храниться во внешнем object storage; Registry содержит их идентификаторы и metadata.

### 6.7 Knowledge and Context

Knowledge Store не является простым накоплением истории разговоров.

Предполагаются типизированные записи: подтверждённые факты, архитектурные решения, открытые гипотезы, отрицательные результаты и связанные с ними источники.

Знания должны иметь область действия — например, personal, repository или project — и возможность пересмотра.

Извлечение контекста осуществляется по запросу, с учётом актуальности, происхождения и разрешений.

Приватные evaluation artifacts не должны попадать в обычный контекст через память или результаты поиска.

### 6.8 Observability and Self-Evaluation

Harness должен измерять собственную эффективность.

Ключевые категории метрик:

- Task success и regression rate.
- Результаты независимых evals.
- Время выполнения и затраты ресурсов.
- Количество ручных исправлений.
- Стоимость и latency дополнительных agent calls.
- Надёжность интеграций.
- Время, затраченное человеком на review.

Изменения в конфигурации harness рассматриваются как экспериментальные изменения, которые можно проверить на фиксированном наборе задач.

## 7. Operational Modes

### 7.1 Interactive Mode — Default

Пользователь запускает привычный Codex или Claude Code.

Агент получает доступ к общим skills и инструментам. Пользователь сам управляет сессией.

Hooks могут запускать диагностику и дополнительные проверки, но полнота их исполнения зависит от конкретной платформы.

**Гарантия режима:** переносимость инструментов и согласованный доступ к общему harness. Не гарантируется принудительное выполнение всех workflow stages.

### 7.2 Gated Mode

Разработка остаётся интерактивной, но принятие результата происходит через независимую проверку.

Например, изменение не получает статус verified, пока необходимые проверки и человеческие approvals не завершены.

Нативный агент может закончить разговор раньше, но это не меняет статус задачи в независимом реестре.

### 7.3 Managed Mode — Optional

Внешний controller запускает агента, предоставляет ограниченный контекст, отслеживает стадии, управляет ресурсами и вызывает evaluators.

Этот режим предназначен для длительных, повторяемых или изолированных процессов.

Исполнителем может быть Codex, Claude или другой совместимый агент.

Managed Mode допускает использование существующих orchestration engines, включая DeepSeek Harness, через заменяемый backend.

### 7.4 CI / Headless Mode

Проверки выполняются без интерактивной агентской сессии.

CI должен иметь возможность принимать или отклонять изменения по независимым результатам проверок.

Это основной режим для enforceable quality gates, когда они связаны с merge/deployment policy.

## 8. Shared Data Contracts

Компоненты harness взаимодействуют через общие, версионированные контракты.

На архитектурном уровне необходимы следующие сущности:

| Contract | Purpose |
|---|---|
| Task Contract | Цель, ограничения и критерии успешности задачи |
| Run Record | Идентификатор выполнения, исполнитель, версия окружения, статус |
| Capability Descriptor | Возможности и ограничения конкретного agent adapter |
| Workflow State | Текущая стадия и история переходов |
| Evaluation Result | Результаты проверок, ограничения и итоговый verdict |
| Artifact Manifest | Происхождение и местоположение артефактов |
| Evidence Record | Связь утверждения с проверкой и её результатом |
| Knowledge Entry | Типизированное знание с источником и областью действия |
| Resource Policy | Допустимые вычислительные затраты и ограничения |

Идентификаторы и форматы должны быть стабильными между агентами.

Внешним потребителям нельзя требовать чтения внутренних логов Codex или Claude Code для получения основных результатов работы.

Формат контрактов проектируется отдельно от выбора конкретного языка реализации.

## 9. Trust, Security and Isolation

Harness предполагает, что агент может ошибаться, следовать нежелательным инструкциям из проектных файлов или непреднамеренно обращаться к чувствительным данным.

Основные границы доверия:

**User ↔ Agent.** Пользователь определяет цели и разрешения. Агент не получает полномочия автоматически только из текстовой инструкции.

**Agent ↔ Project Workspace.** Доступ к проекту ограничивается разрешёнными путями, операциями и секретами.

**Agent ↔ Evaluator.** Исполнитель не должен иметь доступ к защищённым проверкам или возможности изменять критерии принятия результата.

**Agent ↔ Infrastructure.** Доступ к GPU, network, secrets и внешним системам регулируется вне модели.

**Memory ↔ Protected Data.** Не все данные, доступные инфраструктуре, могут быть возвращены агенту через retrieval.

Hooks используются как интеграционный механизм, но не являются единственной границей безопасности.

Для защищённых операций необходимы независимые проверки прав и изоляция исполнения. При отсутствии надёжного механизма enforcement система должна явно отказываться от предоставления соответствующей гарантии.

Перед использованием с корпоративным кодом необходимо отдельно согласовать допустимые внешние модели, хранение данных, телеметрию, секреты и доступ к внутренним ресурсам.

## 10. Source of Truth and Distribution

Предлагается разделять **канонические определения** и **генерируемые интеграционные конфигурации**.

Каноническими являются:

- Shared skills.
- Project policies.
- Workflow definitions.
- Evaluation contracts.
- Core configuration.
- Artifact schemas.

Производными являются:

- Agent-specific registration files.
- Ссылки на skills.
- Конфигурации hooks.
- Инструкционные entrypoints.
- Локальные настройки подключения CLI/MCP.

Изменения канонического определения распространяются в поддерживаемые среды посредством явной процедуры установки или синхронизации.

Интеграционные файлы не редактируются как независимые источники логики.

Для диагностики используется отдельная проверка окружения, определяющая версии компонентов, доступность интеграций и несовпадения конфигураций.

## 11. Relationship with DeepSeek Harness

DeepSeek Harness рассматривается как потенциальный orchestration backend, а не как обязательная основа персональной системы.

DSH предоставляет расширяемую инфраструктуру для исполнения агентов, делегирования, tools и workflows. Однако модель, в которой DSH владеет основной сессией, отличается от выбранной native-first архитектуры.

Предлагаемое решение:

- Не использовать DSH для ежедневного interactive workflow.
- Не переносить в DSH канонические определения skills и evaluators.
- Сохранять возможность подключить DSH для управляемых multi-agent workflows.
- Оценивать DSH как альтернативу собственной реализации сложного controller, если такая необходимость появится.

Harness должен оставаться функциональным при полном отсутствии DSH.

## 12. Alternatives Considered

| Alternative | Decision | Reason |
|---|---|---|
| Только нативные skills | Недостаточно | Не обеспечивает общую независимую систему проверок и артефактов |
| Отдельный стек под каждого агента | Отклонено | Дублирование и vendor lock-in |
| Собственный agent framework с нуля | Отложено | Высокая сложность, повторение существующих возможностей |
| DeepSeek Harness как главный runtime | Не выбран | Конфликт с требованием native-first UX |
| Portable Core + Native Adapters | **Выбран** | Максимальное повторное использование при сохранении нативных интерфейсов |

## 13. Evolution Strategy

### Phase 1 — Portable Foundation

Общий набор skills, проектных инструкций и интеграций с нативными агентами.

Единый CLI и механизм установки конфигураций.

**Outcome:** переносимое окружение без собственного orchestration layer.

### Phase 2 — Verification Foundation

Независимые evaluators, базовые quality gates, structured results и artifact registry.

**Outcome:** результаты работы можно оценивать независимо от исполнителя.

### Phase 3 — Applied ML Infrastructure

Подключение experiment environments, удалённых вычислений, benchmark infrastructure и воспроизводимых экспериментальных артефактов.

**Outcome:** единый контур для applied ML разработки и экспериментов.

### Phase 4 — Knowledge and Learning

Структурированная память, управление контекстом, интерфейсы объяснения и интерактивного исследования.

**Outcome:** накопление подтверждённого инженерного знания между сессиями и агентами.

### Phase 5 — Optional Orchestration

Поддержка managed workflows, нескольких исполнителей, восстановления выполнения и сложных approval gates.

**Outcome:** автоматизация долгих процессов без изменения основного native-first сценария.

Фазы задают архитектурные зависимости, но не требуют полной реализации каждой подсистемы до начала следующей.

## 14. Success Criteria

Архитектура считается успешной, если:

1. Один и тот же канонический skill доступен из Codex и Claude без независимых копий логики.
2. Замена coding agent не требует изменения evaluators, artifact formats и основных workflow contracts.
3. Общие инструменты запускаются как из агентской сессии, так и напрямую из CLI.
4. Результаты проверок и экспериментов сохраняются независимо от истории агентской сессии.
5. При отсутствии критически важной интеграции система явно показывает недоступные гарантии.
6. Защищённые проверки не раскрывают приватные материалы обычному execution agent.
7. Результаты существенных ML-экспериментов можно связать с их кодом, конфигурацией и вычислительной средой.
8. Использование системы не требует постоянной работы отдельного orchestrator.
9. Добавление нового агента ограничивается созданием тонкого adapter и проверкой совместимости.
10. Эффективность расширений harness может измеряться на воспроизводимых задачах.

## 15. Risks and Trade-offs

**Lowest common denominator.** Чрезмерная унификация может ограничивать использование полезных нативных возможностей. Решение: общий минимальный контракт плюс явно объявляемые дополнительные capabilities.

**Configuration drift.** Генерируемые файлы и реальные настройки агентов могут расходиться. Решение: diagnostics, versioning и проверка целостности установки.

**False sense of enforcement.** Пользователь может ошибочно воспринимать рекомендации hooks как строгие гарантии. Решение: явное разделение advisory и enforceable checks.

**Excessive abstraction.** Универсальная архитектура может оказаться сложнее решаемых задач. Решение: реализовывать только востребованные компоненты и избегать преждевременного построения framework.

**Evaluation overfitting.** Многократная настройка агентов и harness на фиксированных проверках может снижать достоверность измерений. Решение: отделять development benchmarks от независимой итоговой оценки.

**Operational overhead.** Изолированные evaluators, хранение данных и remote execution создают дополнительную стоимость. Решение: использовать разные уровни проверки в зависимости от рисков и масштаба задачи.

**Enterprise compatibility.** Личное окружение может конфликтовать с корпоративными политиками доступа и хранения информации. Решение: поддерживать явные project profiles и возможность отключения отдельных интеграций.

## 16. Open Design Questions

1. Должен ли Harness Core оставаться набором локальных библиотек и CLI или со временем иметь отдельный сервис?
2. Где проводить границу между personal и repository-level конфигурацией?
3. Какой минимальный набор capabilities должен поддерживать новый agent adapter?
4. Какие workflows действительно требуют Managed Mode?
5. Какие типы артефактов должны храниться локально, а какие — во внешнем хранилище?
6. Как интегрироваться с существующими ML experiment trackers без создания конкурирующего источника истины?
7. Какие знания допустимо сохранять между проектами и агентами?
8. Как тестировать переносимость workflows с учётом недетерминированности моделей?
9. Какие ограничения безопасности обязательны до подключения корпоративных репозиториев?
10. В какой момент готовый orchestration engine становится выгоднее собственной небольшой реализации?

## 17. Architecture Decision

**Принять Native-First, Agent-Agnostic архитектуру с Portable Core и тонкими Agent Adapters.**

Основные инженерные capabilities реализуются независимо от coding agents, предоставляются через общие интерфейсы и используют версионированные контракты данных.

Codex CLI и Claude Code остаются основными пользовательскими интерфейсами.

Контроль качества, изоляция, хранение артефактов и воспроизводимость располагаются за пределами внутренних agent loops.

Централизованная orchestration рассматривается как дополнительная возможность, а не базовая зависимость.
