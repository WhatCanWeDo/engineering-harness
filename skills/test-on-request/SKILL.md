# Test on Request

Создавай проверяемые свидетельства корректности по открытому контракту задачи. Пользователь выбирает, когда и какие проверки нужны. Этот skill не устанавливает обязательный процесс для каждой правки.

## Обязательное разделение агентов

Все три типа тестов генерирует **другой агент**, не агент-разработчик. Это относится и к новым regression-тестам по найденным контрпримерам. Разработчик формулирует задачу, получает готовые артефакты и исправляет продукт; генерация, перебор тестовых гипотез, отладка тестов и их подробные логи остаются в отдельном контексте.

Перед делегированием прочитай [контракт передачи задачи](references/delegation.md). Запускай генератор с новым контекстом и минимальным task brief, без автоматического наследования всей переписки разработчика. Для adversarial передавай frozen candidate; для заранее подготавливаемых наборов — контракт, интерфейс и разрешённый baseline, но не будущую реализацию. Модель может быть той же: обязательны отдельные agent session/context, а не другой поставщик.

Если среда не умеет запустить отдельного агента, сообщи `generation_unavailable` и подготовь task brief для отдельной сессии; не генерируй тесты сам как скрытый fallback. Изоляция контекста не заменяет права доступа: приватная ветка дополнительно требует защищённого evaluator. Не запускай private-генератора в общей среде, выдавая её за секретную.

## Активация и границы

Начинай только после явной просьбы применить skill или создать/запустить соответствующие тесты. «Напиши тесты» разрешает подготовку подходящих публичных тестов в указанном scope, но не автоматически весь многостадийный цикл. «Полный цикл» включает план всех трёх типов. Уточни только неоднозначный scope или отсутствующий контракт, продолжая независимую подготовку.

Запрос на дизайн тестирования не является запросом запустить эксперименты на продукте. Авторизация относится к текущей задаче; последующие обычные изменения не включают skill автоматически. Не отменяй уже установленные пользователем/проектом обязательные проверки и не расширяй просьбу о тестировании до изменения продукта, если исправления ранее не были разрешены.

Прочитай [протокол](references/protocol.md). Выбери одну операцию:

- **prepare:** до разработки зафиксировать открытый контракт, подготовить публичный набор и организовать подготовку приватного набора доверенным автором.
- **attack:** после фиксации решения искать контрпримеры в пределах его контракта и согласованного бюджета.
- **evaluate:** выполнить выбранные существующие наборы на неизменном snapshot и составить результат.
- **full:** согласованный цикл prepare → разработка с публичными тестами → attack → исправления, если разрешены → evaluate. Ожидание готового решения является нормальным переходом между сессиями, а не поводом выдумать выполненные этапы.

Для выполнения прочитай [рабочие команды](references/execution.md) и [нативное делегирование](references/native-adapters.md). `scripts/testing.py` готовит plan, brief и snapshot, но не заменяет нативный agent loop. Генератор получает [worker instructions](references/worker.md) в brief; ему не нужно повторно вызывать этот skill и создавать ещё одного генератора.

## До подготовки наборов

Установи цель, входной домен, ожидаемое поведение, ограничения, публичные requirement IDs и источник правильного ответа (oracle). Не бери ожидаемые ответы из проверяемого решения как независимый эталон. Существенную неоднозначность вынеси пользователю; не превращай спорное предположение тестировщика в скрытое требование.

Зафиксируй фазу разработки. Если решение уже существует или автор тестов его видел, нельзя назвать новые проверки заранее подготовленными или независимыми от реализации. Пометь их `post_hoc`; они могут быть полезны, но не заменяют precommitted suite.

Для приватной ветки сначала прочитай [границы изоляции](references/private-evaluation.md). Не создавай «секретный» набор в текущем контексте агента, который затем должен разрабатывать решение. Если защищённого evaluator нет, пометь приватную проверку `unavailable`, объясни недостающую возможность и выполняй отдельно разрешённые публичные/adversarial-операции. Не называй отдельную папку, worktree, сессию или subagent с общими правами безопасной изоляцией.

## Публичный набор

Покрой каждое существенное публичное требование понятными примерами, важными границами и уместными свойствами. Не удаляй полезные проверки ради неполноты. Не устанавливай целевой процент вроде «публично только 30% случаев».

Публичные тесты должны давать полезную обратную связь при разработке. Приватные расширяют комбинации/данные/последовательности, а не прячут обязанности программы. Зафиксируй происхождение и версию initial suite; новые regression-тесты могут добавляться с явной историей.

## Приватная оценка и обратная связь

Передавай evaluator только идентификатор выбранного пакета, candidate snapshot и разрешённую политику обратной связи. Не читай пакет приватных тестов от имени агента-разработчика. Проверяй публичную квитанцию evaluator и не подменяй её своим утверждением «прошло».

При провале пользователь выбрал **немедленное раскрытие минимального воспроизводимого контрпримера**. Evaluator минимизирует и воспроизводит его, выпускает разрешённый пакет данных/expected behavior и регистрирует раскрытие. Сохрани этот пример как публичный regression-тест. Сам исходный пакет и остальные кейсы не возвращаются в контекст разработки.

Новый candidate после исправления имеет новый ID. Повторная проверка на использованном наборе полезна, но помечается как адаптивная. Свежий итоговый holdout возможен только из заранее отложенного и ещё не использованного резерва; если его нет, покажи ограничение. Раскрытие контрпримеров не даёт права менять критерии или скрывать прежние провалы.

## Adversarial-проверки

Начинай после фиксации candidate. Поручи отдельному генератору изучить его реализацию и проверить конкретные гипотезы об ошибках: границы, сочетания условий, порядок операций, ошибки зависимостей, численные свойства, состояние и ограничения ресурсов. Генератор выбирает уместные property-based, stateful, differential или metamorphic-проверки без обязательного фреймворка.

Для каждой находки требуются воспроизводимый вход/последовательность, ожидаемое поведение из контракта, наблюдаемый результат и минимизация по доступному бюджету. Если тест требует неоговорённого свойства, пометь `needs_spec_decision`; если падает инфраструктура — `error`; если результат нестабилен — `inconclusive`. Не объявляй любой crash доказанным дефектом продукта.

Не меняй frozen candidate во время атаки. Подтверждённые находки становятся публичными regression-тестами по происхождению `adversarial`; новый исправленный candidate оценивается отдельно. Неограниченный fuzzing, реальные внешние системы и дорогие вычисления не подразумеваются запросом на обычные тесты.

## Выдача результата

Раздельно сообщи статусы public/private/adversarial, snapshot и версии наборов, выполненные команды/ссылки на evidence, подтверждённые находки, раскрытия и ограничения. Различай `pass`, `fail`, `not_run`, `unavailable`, `error`, `inconclusive`. Adversarial-поиск без находок означает только `no_counterexample_found` при указанном бюджете.

Не называй весь результат verified, если обязательная выбранная проверка не выполнена. Не изображай отсутствие запуска как успешную проверку. Код корректности, время выполнения и понимание человека — разные измерения.

## Статус реализации

Версия 0.1: переносимый workflow, CLI-подготовка, шаблоны результатов и нативное делегирование public/adversarial. Python 3.9+ без внешних зависимостей. Private backend, защищённое хранение и enforcement лимитов не реализованы: CLI возвращает unavailable для private. Snapshot даёт проверяемую идентичность, но не защищённую от владельца filesystem неизменность. Запрет неявного подключения задаётся адаптером; общая логика остаётся здесь.
