# Автоматические подпроекты — одна база, общие знания

Подпроект — смысловая группа внутри project_id, а не отдельная SQLite, permission scope или режим запуска агента. Пользователь не вызывает subproject init и не обязан перечислять группы заранее. `workflow start` обнаруживает их автоматически; `workflow ingest` обновляет каталог после curation. Родительский проект по-прежнему инициализируется один раз обычным project init, либо использует существующий legacy store.

## Откуда берутся группы

1. **Компоненты исходников.** Скрипт читает имена файлов, а не их полное содержимое. Package markers: pyproject.toml, package.json, Cargo.toml, go.mod, SKILL.md, __init__.py в подпапках. Также рассматриваются доменные верхние каталоги и children apps/packages/services/components/skills/experiments/workflows/src/lib с минимум двумя файлами. Технические docs/tests/scripts/shared/common/utils не становятся доменами по одному наличию каталога. Вложенные компоненты получают parent_id.
2. **Повторяющиеся темы.** Предметный tag в active project knowledge из минимум двух разных origin_task создаёт виртуальный topic. Одна задача с десятью похожими записями не создаёт десять подтверждений темы. Generic tags вроде python/test/code-map исключены. Смысл tags определяет уже существующий Curator; отдельного LLM-вызова для кластеризации нет. Topic с именем существующего компонента не дублируется.
3. **Неопределённость.** Нет уверенных сигналов — задача остаётся project-wide. Не создавай отдельный подпроект для каждой задачи или предположения.

Поиск файлов использует Git tracked+untracked с ignore rules. Если Git недоступен или root не является его корнем, действует bounded filesystem walk: до 20 000 файлов, глубина до шести каталогов, без hidden/generated/dependency directories и symlinks. Имена secret-файлов вроде .env не входят в каталог. Это не security scan. Ограничения полного обхода возвращаются в inventory.complete; при неполном обходе отсутствие компонента не считается доказанным удалением.

В обычном initialized проекте root берётся из его профиля. В legacy окружении CLI ищет ближайший repository/package root от cwd. API-вызывающий код без root получает только topics из базы; сканирования HOME нет. В headless запуске передавай корректный cwd/--project-root: --db сам по себе не выбирает repository root. В task catalog максимум новых 100 автоматически обнаруженных групп на refresh; исторические groups сохраняются. Scout получает до 12 вариантов, не весь репозиторий.

## Как определяется подпроект задачи

Приоритет:

- `paths` в task.json, если разработчик уже знает затронутые пути. Это описание scope работы, не ручное создание подпроектов. Paths относительные, до 100; можно указывать будущий файл внутри известного компонента. Не подставляй все dirty files из Git без проверки принадлежности задаче.
- Текущий подкаталог, если paths не переданы/пусты.
- Достаточно характерное имя компонента/темы в goal. Короткие или неоднозначные совпадения не используются.
- Project-wide fallback.

Один task может иметь несколько subproject_ids (crosscutting). Для пути выбирается наиболее вложенный компонент. Existing Scout может уточнить выбор по смыслу, особенно при разных языках goal и directory names. В selection.json он возвращает обычный selected_refs и опционально subproject_ids из своего brief:

```json
{"selected_refs":["K-...@1"], "subproject_ids":["S-..."]}
```

`[]` означает project-wide. Это автоматическая работа Scout, не вопрос пользователю перед каждой задачей. Если metadata достаточно, опусти поле. Не выдумывай ID и не создавай новую тему этим ответом.

Каталог для задачи фиксируется при её начале. Перед первым context packet `workflow context` фиксирует уточнение Scout для всех ролей. После первого packet изменить affiliation нельзя; новая тема/перемещение файлов в другой задаче не переписывает старый snapshot. Низкоуровневый `context prepare` тоже закрывает возможность изменения routing при сохранении packet. Старой задаче без каталога не добавляется знание о новых темах задним числом.

## Совместное использование знаний

Не записывай автоматическую классификацию в `applicability.subproject`: applicability — существующий строгий фильтр, а автоматическая эвристика может ошибиться. Для новой организации используются отдельные subproject_ids.

Все обычные project entries остаются доступны всем задачам этого проекта при прежних проверках ролей, состояний, applicability и snapshot. Совпадение с подпроектом даёт небольшой приоритет среди результатов запроса — до двух мест в соответствующем ranking. Exact entry/symbol match сохраняет приоритет. Соседние groups не исключаются из поиска; retrieved top-N всё равно ограничен бюджетом. Scout выбирает полезные sources независимо от affiliation.

Общие записи имеют subproject_ids:[]; Curator может явно указать это. Без поля Core сохраняет прежнюю affiliation для revision существующей записи; для новой использует совпадения symbols/tags с известными группами, затем routing задачи. Явные IDs валидируются по замороженному task catalog. Автоматическая метка не делает candidate подтверждённым и не меняет project/general scope. Повторяющиеся tags также помогают ранжировать старые entries без переписывания claims.

## Стабильность и просмотр

```sh
harness knowledge subprojects --project PROJECT_ID
harness task show --task TASK_ID
```

Первая команда показывает уже обнаруженный каталог; это read-only просмотр, не обязательная инициализация. Вторая показывает выбранные IDs, basis, classification и sealed. Task/result JSON — источник для diagnostics; названия находятся в каталоге.

IDs детерминированы по project_id + kind + relative component path или нормализованному tag, а не по порядку сканирования. Повторный start той же задачи сохраняет каталог/routing. При полном discovery исчезнувший компонент становится retired; его история и знания не удаляются. Переименование directory/tag пока создаёт новую группу с новым ID: автоматического доказательства тождества, merge/split и semantic synonym resolution нет. Shared retrieval сохраняет доступ к прежним фактам.

Дополнительной модели, vector index или отдельного agent loop не требуется. Это объяснимая эвристическая организация с ограниченной семантической помощью уже существующих Scout/Curator, не совершенная модель архитектуры. Пользователь может поправить вывод в текущей задаче до первого packet или задать scope новой задачи; исправление не требует реорганизации файлов и баз.
