# Оценка качества skills

Статус: предложение для harness, 2026-11-03.

Skill полезен, если на реальных задачах улучшает результат при приемлемых затратах и сохраняет управление у пользователя. Корректный frontmatter и убедительно написанные инструкции проверяют только небольшую часть этого утверждения.

## Три разных объекта проверки

1. **Пакет:** обнаружимость, ссылки, зависимости, исполняемые помощники и форматы артефактов.
2. **Поведение агента со skill:** выбор подходящего сценария, следование предпочтениям, качество работы, обработка ошибок и границы разрешений.
3. **Польза человеку:** время review, понимание, количество исправлений и возможность принимать следующие решения.

Прохождение проверки пакета не означает прохождение двух остальных уровней. Независимый агент помогает обнаружить ошибки, но его оценка сама по себе не доказывает педагогическую эффективность или отсутствие утечек ответа.

## Обязательные условия допуска

Не компенсировать провал этих условий высоким средним баллом:

| Условие | Как проверять |
|---|---|
| Выполнено явное требование пользователя | Проверить артефакт и действия против исходного запроса; для understand-changes — HTML, ровно пять MCQ, выбранная глубина и частота |
| Нет существенных неподтверждённых утверждений | Сверить ссылки, код, результаты команд и тестов; неизвестное не выдаётся за проверенное |
| Нет неразрешённых побочных действий | Сравнить состояние файлов/настроек до и после в изолированном окружении |
| Инструменты реально работают | Запустить помощники на валидных, ошибочных и пограничных входах; проверить артефакт в целевом приложении |
| Нет критической неоднозначности задания или ответа | Смысловой reviewer проверяет, что решение/правильный ответ поддержан источниками и единственен в заданных условиях |

Для решения «готово» должны быть указаны конкретные проверенные сценарии и ограничения. Непроверенное помечается `not tested`, а не `pass`.

## Рубрика качества

Для каждой применимой категории использовать шкалу 0–3: 0 — нарушает задачу; 1 — требует существенной ручной правки; 2 — полезно с небольшими замечаниями; 3 — устойчиво работает в нескольких разнообразных прогонах. При отсутствии свидетельств — `not tested`. Оценку сопровождают наблюдением и ссылкой на evidence; по одному примеру нельзя присваивать устойчивость.

| Категория | Наблюдаемый признак | Пример проверки |
|---|---|---|
| Выбор и область применения | Skill включается в нужных сценариях и не захватывает несвязанные задачи | Положительные, пограничные и отрицательные запросы |
| Точность | Рассказ и решения соответствуют фактическим входам | Сверка утверждений с кодом, данными и результатами |
| Полнота и фокус | Существенные требования выполнены без ненужного расширения | Чеклист запроса и список добавленных действий |
| Пользовательское управление | Разовые и постоянные предпочтения различаются, изменения в ходе задачи учитываются | «Только сейчас подробно», «всегда кратко», «объясни сейчас» |
| Качество объяснения | Читатель может объяснить причинность и предсказать поведение | Новый пример после чтения, оценённый по источникам |
| Надёжность | Ошибки видны, повторный запуск не портит данные | Неверный JSON, отсутствующий runtime, существующий output, повреждённые настройки |
| Переносимость | Одинаковый контракт результата сохраняется между средами | Реальные прогоны Codex и Claude на одном сценарии |
| Эффективность | Выигрыш оправдывает время чтения, вызовы и поддержку | Парное сравнение с выполнением того же запроса без skill |
| Поддерживаемость | Правило имеет один источник, ссылки актуальны, код тестируется | Изменение настройки не требует править несколько независимых копий |

## Специальная оценка understand-changes

### Объяснение

Проверить причинную цепочку, пример до/после, ключевые взаимодействия, реальные проверки и ограничения. Сопоставлять содержание со всей затронутой системой, а не только с diff. Не путать краткость с пропуском сведений, необходимых для quiz. Оценивать разные масштабы: небольшая правка, межмодульное изменение, архитектурный документ без реализации.

### Quiz

- Пять вопросов с четырьмя вариантами, один правильный ответ на каждый; все ответы обоснованы исходниками и объяснением.
- Вопросы требуют применять понимание к сценарию. Не принимать пять пересказов одного факта как пять содержательных проверок.
- Неверные ответы правдоподобны и отражают возможные ошибки понимания; объяснение обратной связи не создаёт новых заблуждений.
- Проверять длину, стиль, конкретность, оговорки, позицию, взаимную вложенность вариантов и подсказки из других вопросов. Один правильный длинный ответ не является дефектом.
- Проверять наборы между задачами. История длины/позиций — диагностический сигнал, а не полноценный evaluator стиля или статистическое доказательство.
- Дополнительная слепая проверка: reviewer видит варианты без ключей правильности и оценивает, выделяется ли один по форме. Его догадку нельзя считать чистым измерением утечки: содержание вариантов тоже может позволять решить вопрос. Результат дополняется смысловым разбором.
- HTML до ответа не показывает правильность. После выбора отображает понятное объяснение и поддерживает повторную попытку. Проверяются клавиатура, узкий экран и отсутствие сетевых зависимостей.

Прохождение quiz показывает лишь результат на этих вопросах. Для проверки пользы человеку нужны новые задачи на перенос понимания, а по возможности — повторная проверка спустя время. Эти проверки не смешиваются с обязательными пятью вопросами рабочего документа.

## Процедура независимого прогона

1. Зафиксировать версию skill: Git revision или хеши файлов, доступные инструменты, агент/модель (если известны), настройки, исходные данные и конкретный запрос.
2. Дать независимому исполнителю skill и минимальные исходники. Не передавать предполагаемый ответ, подозреваемую ошибку и предлагаемые исправления.
3. Изолировать его рабочую папку и личные настройки. Исполнитель должен создать реальный артефакт, а не только отрецензировать текст инструкций.
4. Собрать артефакт, результаты команд, изменения файлов, наблюдения о времени и затратах. Не придумывать недоступные метрики.
5. Сверить результат с критериями. По возможности отделять исполнителя от оценщика артефакта. Если это один агент, отметить ограничение, даже если он независим от автора skill.
6. Исправить подтверждённые дефекты. Повторить затронутые проверки; сохранить исходное обнаружение и результат исправления.
7. Для утверждений об устойчивости добавить повторные прогоны, другой агент и отложенные задачи. Development cases остаются отдельными от итоговой оценки.

## Сравнение с базовой линией

Сравнивать обычный запрос без skill с тем же запросом со skill при сопоставимых моделях, инструментах и входах. Заранее выбрать критерии и порядок заданий; по возможности скрыть от оценщика, какой вариант создан со skill. Измерять исправления фактических ошибок, выполнение требований, время до пригодного результата, время чтения и способность человека объяснить новый сценарий.

Единичный удачный пример показывает работоспособность, но не выигрыш относительно базовой линии. Нельзя подменять отсутствие измерений числом вроде «качество 95%».

## Минимальный набор regression cases

| Case | Проверяемое поведение |
|---|---|
| Завершённая задача со средними defaults | Один итоговый HTML, пять вопросов, пауза |
| «В этой задаче подробно» | Глубина меняется, личные настройки не записываются |
| «Всегда кратко» | Предпочтение сохраняется и доступно другому агенту |
| «Объясни сейчас» при on_request/task_end | Разовый разбор не меняет постоянную частоту |
| Исправления внутри одной задачи | Итог объясняет конечное состояние без повторных учебных пауз |
| Новый репозиторий без HEAD | Нет выдуманной baseline и потери новых файлов |
| Изменение только RFC | Предложенный контракт не выдаётся за реализованное поведение |
| Очень маленькая правка | Пять содержательных вопросов без выдуманного scope и повторений |
| Длинный diff с посторонними изменениями | Границы задачи явно установлены, авторство не присвоено |
| Недоступный runtime/сломанные настройки | Честное сообщение, отсутствие ложного успеха |
| Повторный рендер | Существующий артефакт не затирается, история не получает лишний вес |
| Выдача HTML в чате | Готовая ссылка ведёт к существующему неизменяемому артефакту; пробелы/спецсимволы не ломают путь; есть браузерный fallback без поиска файлов |
| Повторное открытие и удалённая сессия | Старый чат открывает тот же документ; агент не открывает браузер на SSH-хосте вместо компьютера читателя |
| Серия quiz | Нет устойчивых формальных подсказок; случайные повторы не исправляются ради симметрии |

Это план оценки. Статус фактически выполненных проверок фиксируется в отдельном отчёте, а не подразумевается из наличия списка.
