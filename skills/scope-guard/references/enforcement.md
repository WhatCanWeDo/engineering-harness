# Когда нужна техническая блокировка

Читай при проектировании обязательного контроля исполнения. Наличие этого документа не означает, что контроль установлен. Внедрение прав, шлюзов и политик — отдельная инженерная задача в разрешённом пользователем объёме.

## Разделение ответственности

```text
Поручение и ограничения → проект операции → независимый исполнитель → целевая система
                                  │                  │
                           предложение агента   защищённая политика
```

Агент предлагает операцию. Исполнитель проверяет канонический объект и среду, вид действия, точные параметры, применимые запреты и версию разрешения. Запрет имеет приоритет над общим разрешением; конкретное разрешённое исключение имеет явно заданные границы, срок или одноразовый характер.

Для реальной границы нужны все условия:
- Политику и исполнитель агент не может самостоятельно ослабить или заменить.
- Разрешение не создаётся только на основании формулировки, которую написал сам исполнитель задачи. Преобразование естественного языка в политику тоже может быть ошибочным: политика должна иметь доверенное основание; не выдавай классификацию другой моделью за гарантию.
- У агента нет обходного доступа на запись: прямых API, широких токенов, альтернативных инструментов или возможности получить их и обойти исполнитель. Проверяется и доступ через общие ресурсы, затрагивающие защищённый объект.
- Исполнитель проверяет фактический запрос и существенные версии непосредственно при применении, насколько позволяет API; отклоняет устаревшие разрешения и неоднозначные цели. Поддерживает отзыв разрешений для ещё не начатых операций.
- Неудачный/прерванный запрос сверяется с фактическим состоянием до повторной отправки. Для одноразовых операций учитываются повторная доставка и ключи идемпотентности.

Если эти условия не обеспечены, называй механизм вспомогательной проверкой, а не обязательным барьером. Даже обязательный барьер гарантирует соблюдение закодированной политики в пределах своей реализации, а не правильное понимание любого текста пользователя.

## Примеры решений

- Сначала разрешено обновить A и B, затем сказано «не трогать объекты с изменениями коллеги». У A найдена сохранённая, ещё не активированная настройка коллеги: A не менять по старому разрешению; B оценить отдельно. Не считать отсутствие деплоя снятием ограничения.
- В массовом обновлении запрещено менять таблицу T. Миграция общей схемы затрагивает T: исключения T из списка прямых целей недостаточно.
- Для папки есть общий запрет, позже пользователь прямо разрешает исправить один названный файл: разрешение относится к этому изменению, не ко всей папке. Повторное подтверждение того же разрешения не нужно.
- Разрешено один раз вернуть ресурсы A, сохранив новый конфиг коллеги: восстановить только разрешённые поля, проверить конфиг, отметить операцию завершённой. Старый полный снимок не является разрешённой целью отката.
- История изменений A недоступна, B однозначно разрешён и не зависит от A: продолжить B, выяснить принадлежность A к исключению, не объявлять весь проект заблокированным.

Эти примеры поясняют решения; сами по себе они не являются выполненными поведенческими тестами.
